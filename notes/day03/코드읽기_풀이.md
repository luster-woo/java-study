## 출력 예측

### 출력 1 · 부모 메서드 안에서 부른 메서드도 동적 바인딩

```java
class A {
    void hello() { System.out.print("A "); }
    void call() { hello(); }
}
class B extends A {
    @Override
    void hello() { System.out.print("B "); }
}

// main
A x = new B();
x.call();
new A().call();
```

**답**

```
B A 
```

- `x.call()` → B에는 call()이 없으니 A의 call() 실행
- 그 안의 `hello()`는 사실 `this.hello()` → **this = 실제 객체 = B** → B의 hello → `B `
- `new A().call()` → 실제 객체가 A → A의 hello → `A `

**핵심**: 부모 클래스 코드 안에서 호출해도, 재정의된 메서드는 **항상 실제 객체 기준**(동적 바인딩)으로 실행된다. "A 클래스 안이니까 A의 hello겠지"가 함정.

### 출력 2 · 생성자 호출 순서

```java
class P { P() { System.out.print("P "); } }
class C extends P { C() { System.out.print("C "); } }
class G extends C { G() { super(); System.out.print("G "); } }

// main
new G();
```

**답**

```
P C G 
```

모든 생성자의 첫 줄에는 `super()`가 있다 (안 쓰면 컴파일러가 자동으로 넣음).

```
G() → super() 호출, 아직 G 출력 안 함
  C() → super() 자동 호출, 아직 C 출력 안 함
    P() → super() → Object() → 돌아와서 "P "
  돌아와서 "C "
돌아와서 "G "
```

→ **가장 위 조상부터** 만들어진다. 부모 부분이 먼저 완성돼야 자식이 그걸 쓸 수 있으니까.
(D2 출력 3의 `this()` 체인과 같은 원리)

### 출력 3 · equals 재정의 안 하면

```java
class Pt {
    int x;
    Pt(int x) { this.x = x; }
}

Pt p = new Pt(1);
Pt q = new Pt(1);
System.out.println(p == q);
System.out.println(p.equals(q));
List<Pt> list = new ArrayList<>(List.of(p));
System.out.println(list.contains(q));
```

**답**

```
false
false
false
```

- `p == q` → new를 두 번 했으니 다른 객체 → false
- `p.equals(q)` → 재정의 안 했으니 **Object의 equals = `==`** → false
- `list.contains(q)` → contains는 내부에서 **equals**로 비교 → false

**핵심**: 컬렉션(List, Set, Map)은 전부 equals(와 hashCode)로 같은지 판단한다. 내용으로 비교되게 하려면 재정의 필수.

## 버그 찾기

### 버그 1 · Dog가 안 나온다

```java
class Animal {
    public String toString() { return "Animal"; }
}
class Dog extends Animal {
    public String tostring() { return "Dog"; }
}

System.out.println(new Dog());   // Animal 출력
```

**문제점**

- `tostring` (소문자 s) 오타 → 재정의가 아니라 **이름이 다른 새 메서드**가 생김
- 에러도 경고도 없어서 찾기 어렵다
- println은 `toString()`을 부르는데 Dog엔 없으니 → 부모 Animal의 toString → `Animal`

**수정**

```java
@Override
public String toString() { return "Dog"; }
```

→ `@Override`를 붙여두면 오타 상태에서 **"재정의할 메서드가 없다"**는 컴파일 에러로 바로 잡아준다. 재정의할 땐 항상 `@Override`.

### 버그 2 · 실행 중 에러

```java
Animal a = new Cat();
Dog d = (Dog) a;
d.fetch();
```

**문제점**

- 실제 객체가 Cat인데 Dog로 다운캐스팅 → 실행 중 **ClassCastException**
- 컴파일은 통과한다 (Animal 변수가 Dog를 가리킬 "수도" 있으니까)

**수정** : 캐스팅 전에 instanceof로 확인

```java
if (a instanceof Dog dog) {
    dog.fetch();
}
```

## 빈칸 채우기

### 빈칸 1 · equals 재정의

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Point p)) return false;
    return x == p.x && y == p.y;
}
```

| 줄 | 의미 |
|---|---|
| `this == o` → `true` | 같은 객체면 비교할 필요도 없이 같음 (빠른 탈출) |
| `!(o instanceof Point p)` → `false` | Point가 아니거나 null이면 다름. 맞으면 p로 형변환까지 |
| `x == p.x && y == p.y` | 내용 비교. int는 기본형이라 `==`로 비교 |

### 빈칸 2 · 관리자 급여

```java
Manager(String name, int base, int team) {
    super(name, base);
    this.team = team;
}

@Override
int pay() { return super.pay() + team * 100000; }
```

- `super(name, base)` : Employee에 **기본 생성자가 없다** → 안 쓰면 컴파일러가 `super()`를 넣는데 그런 생성자가 없어서 **컴파일 에러**
- `super.pay()` : 부모의 급여 계산 재사용. `base`라고 써도 지금은 같지만, 나중에 부모 계산식이 바뀌면 `super.pay()`가 자동으로 따라간다
- ⚠️ `pay()`라고만 쓰면 자기 자신(Manager.pay)을 다시 호출 → 무한 반복

## 핵심 정리

| 함정 | 기억할 것 |
|---|---|
| 부모 메서드 안의 호출 | `hello()` = `this.hello()` → 실제 객체의 재정의된 메서드 |
| 생성자 순서 | 첫 줄 `super()` 자동 → 최상위 조상부터 실행 |
| 부모에 기본 생성자 없음 | 자식 생성자에서 `super(...)` 직접 호출 필수 |
| equals 미재정의 | `==`와 같음 → `contains`, `Set` 중복 제거 전부 실패 |
| 메서드 이름 오타 | 에러 없이 새 메서드가 생김 → `@Override`로 방지 |
| 다운캐스팅 | 컴파일 OK, 실행 중 ClassCastException → `instanceof` 먼저 |
| `super.pay()` vs `pay()` | super 빼면 자기 자신 호출 → 무한 반복 |
