## 한 줄 요약

JPA에서 가장 중요한 2가지는 **① 객체-RDB 매핑**과 **② 영속성 컨텍스트**. 영속성 컨텍스트가 애플리케이션과 DB 사이에서 1차 캐시·쓰기 지연·변경 감지를 해준다.

---

## 1. 영속성 컨텍스트

- "**엔티티를 영구 저장하는 환경**"
- `em.persist(entity)`는 DB 저장이 아니라 **영속성 컨텍스트에 넣는 것**
- 눈에 안 보이는 **논리적 개념**, 엔티티 매니저를 통해 접근
  - J2SE 환경: 엔티티 매니저 : 영속성 컨텍스트 = **1:1**
  - 스프링 같은 컨테이너 환경: **N:1** (같은 트랜잭션이면 같은 영속성 컨텍스트 공유)

---

## 2. 엔티티의 생명주기

| 상태 | 설명 | 코드 |
|---|---|---|
| **비영속** (new/transient) | 영속성 컨텍스트와 전혀 관계없는 새 객체 | `new Member()` |
| **영속** (managed) | 영속성 컨텍스트에 **관리**되는 상태 | `em.persist(member)`, `em.find()` |
| **준영속** (detached) | 저장되었다가 **분리**된 상태 | `em.detach(member)` |
| **삭제** (removed) | 삭제된 상태 | `em.remove(member)` |

```java
Member member = new Member();           // 비영속
member.setId("member1");
EntityManager em = emf.createEntityManager();
em.getTransaction().begin();
em.persist(member);                     // 영속 — 이때 DB에 쿼리가 나가는 게 아님!
em.detach(member);                      // 준영속
em.remove(member);                      // 삭제
```

## 3. 영속성 컨텍스트의 이점

1차 캐시 · 동일성 보장 · 쓰기 지연 · **변경 감지** · 지연 로딩

### ① 1차 캐시

- 영속성 컨텍스트 내부에 `Map<@Id, Entity>` 형태의 1차 캐시가 있음

```java
em.persist(member);                                     // 1차 캐시에 저장
Member a = em.find(Member.class, "member1");            // 1차 캐시에서 조회 (SQL X)
Member b = em.find(Member.class, "member2");            // 캐시에 없음 → DB 조회 → 1차 캐시에 저장 → 반환
```

- 트랜잭션 단위로 생겼다 사라지는 캐시라 성능 이득은 크지 않음 (여러 사용자가 공유하는 건 2차 캐시)

### ② 영속 엔티티의 동일성 보장

```java
Member a = em.find(Member.class, "member1");
Member b = em.find(Member.class, "member1");
a == b  // true
```

- 1차 캐시 덕분에 **REPEATABLE READ** 수준의 격리를 DB가 아닌 **애플리케이션 차원**에서 제공

### ③ 트랜잭션을 지원하는 쓰기 지연 (엔티티 등록)

```java
transaction.begin();
em.persist(memberA);   // 1차 캐시 저장 + INSERT SQL을 '쓰기 지연 SQL 저장소'에 쌓음
em.persist(memberB);
// 여기까지 INSERT SQL을 DB에 보내지 않음
transaction.commit();  // 커밋 순간 flush → 쌓인 SQL 전송 → DB 커밋
```

- 모아서 보낼 수 있으니 JDBC 배치 활용 가능

> 참고: 하이버네이트는 `hibernate.jdbc.batch_size` 옵션으로 지정한 개수만큼 모아서 한 번에 보낸다.

### ④ 변경 감지 (Dirty Checking) — 엔티티 수정

```java
transaction.begin();
Member memberA = em.find(Member.class, "memberA"); // 영속 엔티티 조회
memberA.setUsername("hi");                         // 값만 바꾸면
memberA.setAge(10);
// em.update(member) 같은 코드가 필요 없다!
transaction.commit();                              // UPDATE 자동 실행
```

동작 원리 (flush 시점)
1. 1차 캐시에는 엔티티와 함께 **최초 로딩 시점의 스냅샷**이 저장되어 있음
2. flush 때 엔티티와 스냅샷을 **비교**
3. 바뀐 게 있으면 UPDATE SQL 생성 → 쓰기 지연 SQL 저장소에 넣음
4. DB에 SQL 전송 → 커밋

### ⑤ 엔티티 삭제

```java
Member memberA = em.find(Member.class, "memberA");
em.remove(memberA);  // 커밋 시점에 DELETE
```

## 4. 플러시 (flush)

> 영속성 컨텍스트의 **변경 내용을 DB에 반영**하는 것

플러시가 발생하면
- 변경 감지
- 수정된 엔티티의 SQL을 쓰기 지연 SQL 저장소에 등록
- 쓰기 지연 SQL 저장소의 쿼리를 DB에 전송 (등록·수정·삭제)

플러시하는 방법

| 방법 | |
|---|---|
| `em.flush()` | 직접 호출 (테스트 외엔 거의 안 씀) |
| 트랜잭션 커밋 | 자동 호출 |
| **JPQL 쿼리 실행** | 자동 호출 |

JPQL 실행 시 자동 플러시되는 이유

```java
em.persist(memberA);
em.persist(memberB);
em.persist(memberC);
// 아직 DB엔 INSERT가 안 나간 상태에서
List<Member> members = em.createQuery("select m from Member m", Member.class).getResultList();
// → 플러시를 안 하면 A, B, C가 조회되지 않음. 그래서 JPQL 전에 자동 플러시
```

플러시 모드: `em.setFlushMode(FlushModeType.COMMIT)`
- `AUTO` (기본값): 커밋이나 쿼리 실행 시 플러시 — **그냥 기본값 쓰면 됨**
- `COMMIT`: 커밋할 때만

**플러시는!**
- 영속성 컨텍스트를 **비우지 않음** (1차 캐시 유지)
- 영속성 컨텍스트의 변경 내용을 DB에 **동기화**
- 트랜잭션이라는 작업 단위가 중요 → **커밋 직전에만 동기화하면 됨**

## 5. 준영속 상태

- 영속 → 준영속: 영속성 컨텍스트에서 **분리(detached)**
- 영속성 컨텍스트가 제공하는 기능(변경 감지, 지연 로딩 등)을 **사용 못 함**

| 메서드 | 효과 |
|---|---|
| `em.detach(entity)` | 특정 엔티티만 준영속 |
| `em.clear()` | 영속성 컨텍스트 **완전히 초기화** (테스트에서 1차 캐시 없이 DB 조회 결과 보고 싶을 때 자주 씀) |
| `em.close()` | 영속성 컨텍스트 종료 |

```java
Member member = em.find(Member.class, 150L);
member.setName("AAAAA");
em.detach(member);   // 준영속
tx.commit();         // UPDATE 안 나감
```

> 참고: 준영속 엔티티를 다시 영속으로 만들려면 `em.merge()`. 준영속 상태에서 지연 로딩을 건드리면 `LazyInitializationException` ([8장](08_프록시와_연관관계_관리.md)).

## 면접 포인트

- **영속성 컨텍스트의 이점 5가지?** 1차 캐시, 동일성 보장, 트랜잭션을 지원하는 쓰기 지연, 변경 감지, 지연 로딩.
- **변경 감지 원리?** 최초 조회 시 스냅샷을 떠두고 flush 때 엔티티와 비교해 바뀐 필드로 UPDATE를 만든다. 영속 상태에서만 동작.
- **flush가 일어나는 시점, flush하면 1차 캐시가 비워지나?** `em.flush()`, 커밋, JPQL 실행 시. 비워지지 않고 DB와 동기화만 한다.
