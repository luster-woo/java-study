## 한 줄 요약

객체 상속 ↔ DB 슈퍼타입-서브타입 모델을 매핑한다. **기본은 조인 전략, 단순하면 단일 테이블.** 공통 필드(등록일·수정일)만 물려줄 땐 `@MappedSuperclass`.

---

## 1. 상속관계 매핑

- RDB는 상속 관계 X. 대신 **슈퍼타입-서브타입 관계**라는 모델링 기법이 객체 상속과 유사
- 논리 모델을 물리 모델로 구현하는 3가지 방법

| 방법 | 전략 |
|---|---|
| 각각 테이블로 변환 | **조인 전략** `JOINED` |
| 통합 테이블로 변환 | **단일 테이블 전략** `SINGLE_TABLE` |
| 서브타입 테이블로 변환 | **구현 클래스마다 테이블 전략** `TABLE_PER_CLASS` |

### 주요 어노테이션

```java
@Entity
@Inheritance(strategy = InheritanceType.JOINED)   // JOINED / SINGLE_TABLE / TABLE_PER_CLASS
@DiscriminatorColumn(name = "DTYPE")              // 구분 컬럼 (기본 이름 DTYPE)
public abstract class Item {
    @Id @GeneratedValue
    private Long id;
    private String name;
    private int price;
}

@Entity
@DiscriminatorValue("A")                          // DTYPE에 들어갈 값 (기본값: 엔티티 이름)
public class Album extends Item {
    private String artist;
}
// Movie(director, actor), Book(author, isbn)도 같은 방식
```

- **전략만 바꿔도 코드는 그대로** — JPA의 큰 장점
- `@Inheritance`를 생략하면 기본값은 `SINGLE_TABLE`

### ① 조인 전략 (JOINED) — 기본으로 생각

ITEM(ID, NAME, PRICE, DTYPE) + ALBUM(ITEM_ID, ARTIST), MOVIE(…), BOOK(…) — 자식 PK가 부모 PK를 겸한 FK

| 장점 | 단점 |
|---|---|
| **테이블 정규화** | 조회 시 조인 많이 사용 → 성능 저하 |
| **외래 키 참조 무결성** 제약조건 활용 (주문은 ITEM만 보면 됨) | 조회 쿼리가 복잡 |
| 저장공간 효율화 | 저장 시 **INSERT 2번** |

- `@DiscriminatorColumn`이 없어도 동작하지만 DB만 볼 때 어떤 타입인지 알기 어려우니 **넣는 걸 권장**

### ② 단일 테이블 전략 (SINGLE_TABLE)

ITEM 테이블 하나에 ID, NAME, PRICE, ARTIST, DIRECTOR, ACTOR, AUTHOR, ISBN, DTYPE 전부

| 장점 | 단점 |
|---|---|
| 조인 없음 → **일반적으로 조회 성능 빠름** | **자식 엔티티가 매핑한 컬럼은 모두 null 허용** |
| 조회 쿼리 단순 | 테이블이 커질 수 있고, 상황에 따라 오히려 느려질 수 있음 |

- 구분 컬럼 **필수** → `@DiscriminatorColumn`을 안 써도 DTYPE이 자동 생성됨

### ③ 구현 클래스마다 테이블 전략 (TABLE_PER_CLASS) — 쓰지 말 것

ALBUM(ID, NAME, PRICE, ARTIST), MOVIE(…), BOOK(…) — 부모 테이블 없음

- **DB 설계자와 ORM 전문가 둘 다 추천 X**
- 장점: 서브 타입을 명확히 구분할 때 효과적, `not null` 제약 사용 가능
- 단점: **여러 자식 테이블을 함께 조회할 때 느림 (UNION SQL)**, 자식 테이블 통합 쿼리 어려움
  - `em.find(Item.class, id)` 하면 모든 자식 테이블을 UNION ALL로 뒤짐

### 선택 가이드

- 기본은 **조인 전략** (정규화, 객체와 잘 맞음)
- 정말 단순하고 확장 가능성이 낮으면 **단일 테이블**
- 비즈니스적으로 중요하고 복잡하면 조인 전략, 트레이드오프를 DBA와 협의

## 2. @MappedSuperclass

- **공통 매핑 정보**가 필요할 때 (id, name / 등록일, 수정일, 등록자, 수정자)
- DB 테이블은 각자 컬럼을 가짐, 객체만 부모 클래스로 묶는 것

```java
@MappedSuperclass
public abstract class BaseEntity {
    private String createdBy;
    private LocalDateTime createdDate;
    private String lastModifiedBy;
    private LocalDateTime lastModifiedDate;
}

@Entity
public class Member extends BaseEntity { ... }
```

특징
- **상속관계 매핑 X**, **엔티티 X**, 테이블과 매핑 X
- 자식 클래스에 **매핑 정보만** 제공
- 조회·검색 불가 (`em.find(BaseEntity.class, …)` 불가)
- 직접 생성할 일이 없으므로 **추상 클래스 권장**
- 참고: `@Entity` 클래스는 **엔티티나 `@MappedSuperclass`로 지정한 클래스만 상속** 가능

> 참고: 스프링 데이터 JPA의 Auditing(`@CreatedDate`, `@LastModifiedDate` + `@EntityListeners(AuditingEntityListener.class)`)과 함께 쓰면 등록·수정 시간이 자동으로 채워진다.

## 3. 실전 예제 4 — 상속관계 매핑

- 요구사항: 상품 종류는 **음반, 도서, 영화**(이후 확장 가능), 모든 데이터는 **등록일·수정일 필수**
- `Item`(abstract) ← `Album`(artist, etc), `Book`(author, isbn), `Movie`(director, actor)
- 모든 엔티티가 `BaseEntity`(`@MappedSuperclass`) 상속

---

## 면접 포인트

- **상속관계 매핑 전략 3가지와 장단점?** 조인(정규화·무결성 / 조인·INSERT 2번), 단일 테이블(빠른 조회·단순 / 자식 컬럼 null 허용·테이블 비대), 구현 클래스마다(비추천, UNION).
- **`@MappedSuperclass` vs 상속관계 매핑?** `@MappedSuperclass`는 매핑 정보만 물려주고 테이블·엔티티가 아님(조회 불가). 상속관계 매핑은 부모도 엔티티라 부모 타입으로 조회 가능.
