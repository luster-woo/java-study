## 한 줄 요약

객체의 **참조**와 테이블의 **외래 키**를 매핑한다. 양방향이면 둘 중 **외래 키가 있는 쪽을 연관관계의 주인**으로 정하고, 반대편은 `mappedBy`로 읽기 전용.

### 용어

- **방향**: 단방향, 양방향
- **다중성**: N:1, 1:N, 1:1, N:M
- **연관관계의 주인(Owner)**: 객체 양방향 연관관계는 관리 주인이 필요

---

## 1. 연관관계가 필요한 이유

> "객체지향 설계의 목표는 자율적인 객체들의 **협력 공동체**를 만드는 것이다." — 조영호, 『객체지향의 사실과 오해』

시나리오: 회원과 팀이 있고, 회원은 하나의 팀에만 소속 → **회원 : 팀 = N : 1**

### 테이블에 맞춘 모델링 (외래 키를 그대로 사용)

```java
@Entity
public class Member {
    @Id @GeneratedValue
    private Long id;
    @Column(name = "USERNAME")
    private String name;
    @Column(name = "TEAM_ID")
    private Long teamId;      // ← 참조 대신 FK 값
}
```

```java
member.setTeamId(team.getId());                               // 저장: 식별자를 직접 다룸
Member findMember = em.find(Member.class, member.getId());
Team findTeam = em.find(Team.class, findMember.getTeamId());  // 조회: 다시 식별자로 조회 — 객체지향적이지 않음
```

- 테이블은 **외래 키로 조인**, 객체는 **참조**로 연관 객체를 찾음 → 이 간격 때문에 데이터 중심 모델링으로는 **협력 관계를 만들 수 없다**

## 2. 단방향 연관관계

```java
@Entity
public class Member {
    @Id @GeneratedValue
    private Long id;
    @Column(name = "USERNAME")
    private String name;

    @ManyToOne                      // Member 입장에서 N:1
    @JoinColumn(name = "TEAM_ID")   // 매핑할 FK 컬럼
    private Team team;
}
```

```java
// 저장
Team team = new Team();
team.setName("TeamA");
em.persist(team);

Member member = new Member();
member.setName("member1");
member.setTeam(team);           // 참조 저장 → JPA가 TEAM_ID FK에 넣어줌
em.persist(member);

// 조회 — 객체 그래프 탐색
Team findTeam = em.find(Member.class, member.getId()).getTeam();

// 수정
member.setTeam(teamB);          // FK 업데이트
```

## 3. 양방향 연관관계와 연관관계의 주인 ★

### 양방향 매핑

- 테이블은 **변화 없음** (FK 하나로 양쪽 조인 가능)
- Team에 컬렉션만 추가

```java
@Entity
public class Team {
    @Id @GeneratedValue
    private Long id;
    private String name;

    @OneToMany(mappedBy = "team")              // Member.team 필드에 의해 매핑됨
    private List<Member> members = new ArrayList<>();  // 초기화 관례 (NPE 방지)
}
```

```java
int size = em.find(Team.class, teamId).getMembers().size();   // 역방향 탐색
```

### 객체와 테이블이 관계를 맺는 차이 — mappedBy가 어려운 이유

| | 연관관계 수 |
|---|---|
| **객체** | 2개: 회원 → 팀 (단방향), 팀 → 회원 (단방향) |
| **테이블** | 1개: 회원 ↔ 팀 (FK 하나로 양방향) |

- 객체의 양방향은 사실 **서로 다른 단방향 2개**
- 테이블은 `MEMBER.TEAM_ID` **FK 하나**로 양쪽 조인 가능
- 그럼 `Member.team`을 바꿨을 때와 `Team.members`를 바꿨을 때 중 **어느 쪽 값으로 FK를 업데이트?** → **둘 중 하나로 외래 키를 관리해야 함**

### 연관관계의 주인 (Owner) — 양방향 매핑 규칙

- 객체의 두 관계 중 하나를 주인으로 지정
- **주인만이 외래 키를 관리**(등록, 수정)
- **주인이 아닌 쪽은 읽기만** 가능
- 주인은 `mappedBy` 사용 X / 주인이 아니면 `mappedBy`로 주인 지정

### 누구를 주인으로? → **외래 키가 있는 곳**

- 여기서는 `Member.team`이 주인 (MEMBER 테이블에 FK가 있음 = N 쪽 = `@ManyToOne` 쪽)
- Team.members를 주인으로 하면 Team을 수정했는데 MEMBER 테이블 UPDATE가 나가서 헷갈리고, 성능 이슈도 있음
- 비즈니스 중요도로 정하는 게 아님. **"진짜 매핑"과 "가짜 매핑(읽기 전용)"** 으로 이해

### 가장 많이 하는 실수 — 주인에 값을 안 넣음

```java
Member member = new Member();
member.setName("member1");
team.getMembers().add(member);   // 역방향(주인 아님)만 설정
em.persist(member);
// 결과: MEMBER.TEAM_ID = null
```

```java
team.getMembers().add(member);
member.setTeam(team);            // ** 주인에 값 설정 → TEAM_ID 정상 저장
em.persist(member);
```

### 양방향 연관관계 주의 ★

1. **순수 객체 상태를 고려해 항상 양쪽에 값을 설정**
   - 주인에만 넣으면 DB는 맞지만, flush·clear 전엔 1차 캐시의 `team.getMembers()`가 비어 있음 (테스트 코드에서도 문제)
2. **연관관계 편의 메서드**를 만들자 — 한쪽에서 양쪽을 세팅

```java
// Member
public void changeTeam(Team team) {   // 단순 setter와 구분되게 이름 짓기
    this.team = team;
    team.getMembers().add(this);
}
```
   - 편의 메서드는 **한쪽에만** 둔다 (양쪽에 있으면 꼬임)
3. **무한 루프 조심**: `toString()`, Lombok, JSON 생성 라이브러리
   - Member.toString → team.toString → members.toString → … `StackOverflowError`
   - 컨트롤러에서 **엔티티를 그대로 반환하지 말고 DTO로 변환**

### 양방향 매핑 정리

- **단방향 매핑만으로 이미 연관관계 매핑은 완료**
- 양방향은 반대 방향 조회(객체 그래프 탐색) 기능이 추가된 것뿐
- JPQL에서 역방향 탐색할 일이 많긴 함
- **단방향으로 잘 설계하고, 양방향은 필요할 때 추가** (테이블에 영향 없음)
- 주인은 비즈니스 로직이 아니라 **외래 키 위치** 기준

## 4. 실전 예제 2 — 연관관계 매핑 시작

- 테이블 구조는 그대로, **객체가 참조를 사용하도록** 변경
- `Order.member` (`@ManyToOne`, 주인) ↔ `Member.orders` (`@OneToMany(mappedBy = "member")`)
- `OrderItem.order`, `OrderItem.item` (`@ManyToOne`)
- `Order.orderItems` (`@OneToMany(mappedBy = "order")`) + `addOrderItem()` 편의 메서드
- 강의 포인트: 회원이 주문 목록을 갖는 건 좋은 설계가 아닐 수 있음 (주문에서 회원 FK로 찾으면 됨) — 관심사를 끊어내는 게 좋다. 예제라서 넣은 것

## 면접 포인트

- **연관관계의 주인이란?** 양방향 관계에서 외래 키를 관리(등록·수정)하는 쪽. 외래 키가 있는 테이블의 엔티티(보통 N 쪽)를 주인으로 하고 반대편은 mappedBy로 읽기 전용.
- **양방향에서 반대편에만 값을 넣으면?** FK가 null로 저장됨. 주인에 넣어야 하며 객체 일관성을 위해 양쪽 다 세팅(편의 메서드).
- **양방향 매핑 시 무한 루프?** toString·JSON 직렬화가 서로를 계속 호출. 엔티티 직접 반환 대신 DTO 사용.
