## 한 줄 요약

**다대일(N:1) 단방향/양방향이 기본.** 일대다 단방향은 피하고, 일대일은 주 테이블에 FK, 다대다는 연결 엔티티로 풀어라.

---

## 1. 연관관계 매핑 시 고려사항 3가지

| 고려사항 | 내용 |
|---|---|
| **다중성** | `@ManyToOne` / `@OneToMany` / `@OneToOne` / `@ManyToMany` (헷갈리면 반대편 기준으로 생각) |
| **단방향 vs 양방향** | 테이블: FK 하나로 양쪽 조인, 방향 개념 없음 / 객체: 참조 필드가 있는 쪽으로만 참조 가능 |
| **연관관계의 주인** | 객체 양방향은 참조가 2군데 → FK를 관리할 참조를 지정. 반대편은 단순 조회만 |

> 표기 규칙: **왼쪽이 연관관계의 주인**. 다대일 = N(주인) : 1

---

## 2. 다대일 [N:1] — 가장 많이 사용

```java
// 단방향
@Entity class Member {
    @ManyToOne @JoinColumn(name = "TEAM_ID")
    private Team team;
}
// 양방향: Team에 추가
@OneToMany(mappedBy = "team")
private List<Member> members = new ArrayList<>();
```

- 외래 키가 있는 쪽(N)이 주인, 양쪽을 서로 참조하도록 개발
- 다대일의 반대는 일대다

---

## 3. 일대다 [1:N] — 권장 X

### 일대다 단방향

```java
@Entity class Team {
    @OneToMany
    @JoinColumn(name = "TEAM_ID")   // MEMBER 테이블의 FK를 Team이 관리
    private List<Member> members = new ArrayList<>();
}
```

- **1(Team)이 연관관계의 주인**인데, 테이블에서 FK는 **항상 N(MEMBER) 쪽**에 있음 → **반대편 테이블의 FK를 관리하는 특이한 구조**
- `@JoinColumn`을 꼭 써야 함. 안 쓰면 **조인 테이블 방식**(중간 테이블 TEAM_MEMBERS 추가)이 됨
- **단점**
  - 엔티티가 관리하는 FK가 다른 테이블에 있음 → Team을 건드렸는데 MEMBER UPDATE가 나가서 운영 시 헷갈림
  - 연관관계 관리를 위해 **추가 UPDATE SQL** 실행 (INSERT MEMBER 후 UPDATE MEMBER SET TEAM_ID)
- → **일대다 단방향보다는 다대일 양방향을 사용하자** (객체 설계를 약간 양보하더라도)

### 일대다 양방향

- 공식적으로 존재 X
- `@ManyToOne @JoinColumn(name = "TEAM_ID", insertable = false, updatable = false)` — **읽기 전용 필드**로 양방향처럼 쓰는 편법
- → **다대일 양방향을 사용하자**

---

## 4. 일대일 [1:1]

- 반대도 일대일. **주 테이블 / 대상 테이블 중 어디에 FK를 둘지 선택** 가능
- FK에 **DB 유니크(UNI) 제약** 추가
- 예: 회원(Member) — 사물함(Locker), 회원이 주 테이블

| 경우 | 매핑 |
|---|---|
| 주 테이블에 FK, 단방향 | 다대일 단방향과 유사 — `Member`에 `@OneToOne @JoinColumn(name = "LOCKER_ID") Locker locker` |
| 주 테이블에 FK, 양방향 | FK가 있는 곳이 주인, 반대편(`Locker.member`)은 `@OneToOne(mappedBy = "locker")` |
| 대상 테이블에 FK, 단방향 | **JPA 지원 X** |
| 대상 테이블에 FK, 양방향 | 지원. 대상 엔티티(`Locker.member`)를 주인으로 — 사실 위의 양방향과 매핑 방법 같음 |

### 어디에 FK를 둘까?

| | 주 테이블에 FK | 대상 테이블에 FK |
|---|---|---|
| 선호 | 객체지향 개발자 | 전통적인 DB 개발자 |
| 장점 | JPA 매핑 편리, **주 테이블만 조회해도** 대상 데이터 유무 확인 가능 | 1:1 → **1:N으로 바뀌어도 테이블 구조 유지** |
| 단점 | 값이 없으면 FK에 null 허용 | **프록시 한계로 지연 로딩을 설정해도 항상 즉시 로딩** |

- 대상 테이블 FK가 즉시 로딩되는 이유: Member를 로딩할 때 locker 필드에 프록시를 넣을지 null을 넣을지 알려면 어차피 LOCKER 테이블을 조회해야 함 ([8장 프록시](08_프록시와_연관관계_관리.md))

## 5. 다대다 [N:M] — 실무 사용 X

- RDB는 정규화된 테이블 2개로 다대다 표현 불가 → **연결 테이블**을 추가해 1:N, N:1로 풀어야 함
- 객체는 컬렉션으로 객체 2개만으로 다대다 가능
- `@ManyToMany` + `@JoinTable(name = "MEMBER_PRODUCT")`로 연결 테이블 지정, 단방향·양방향 가능

### 한계

- 편리해 보이지만 **실무에서 사용 X**
- 연결 테이블이 단순히 연결만 하고 끝나지 않음 → **주문 시간, 수량** 같은 데이터가 들어옴 (필드 추가 불가)
- 연결 테이블이 숨겨져 있어 예상 못 한 쿼리가 나감

### 극복 — 연결 테이블을 엔티티로 승격

```java
@Entity
public class MemberProduct {   // 사실상 '주문(Order)' 같은 의미 있는 이름이 더 좋음
    @Id @GeneratedValue
    private Long id;           // 강의 권장: 복합키(MEMBER_ID+PRODUCT_ID) 대신 의미 없는 대리키

    @ManyToOne @JoinColumn(name = "MEMBER_ID")
    private Member member;
    @ManyToOne @JoinColumn(name = "PRODUCT_ID")
    private Product product;

    private int count;
    private int price;
    private LocalDateTime orderDateTime;
}
```

- `@ManyToMany` → **`@OneToMany` + `@ManyToOne`**

## 6. 실전 예제 3 — 배송, 카테고리 추가

- 주문 : 배송 = **1:1** (`Order.delivery`에 FK, 주인)
- 상품 : 카테고리 = **N:M** (`@ManyToMany` + `@JoinTable(name = "CATEGORY_ITEM")`로 예제만)
- 카테고리는 계층 구조 → 자기 자신을 참조 (`@ManyToOne parent`, `@OneToMany(mappedBy = "parent") child`)
- 결론: **실전에서는 `@ManyToMany` 사용 X** — 중간 테이블이 단순하지 않고, 필드 추가 불가, 엔티티·테이블 불일치

## 7. 주요 어노테이션 속성

### @JoinColumn — 외래 키 매핑

| 속성 | 설명 | 기본값 |
|---|---|---|
| `name` | 매핑할 FK 이름 | 필드명 + `_` + 참조 테이블의 PK 컬럼명 |
| `referencedColumnName` | FK가 참조하는 대상 테이블의 컬럼명 | 참조 테이블의 PK 컬럼명 |
| `foreignKey` (DDL) | FK 제약조건 직접 지정 (테이블 생성 시만) | |
| `unique`, `nullable`, `insertable`, `updatable`, `columnDefinition`, `table` | `@Column`과 같음 | |

### @ManyToOne / @OneToMany

| 속성 | 설명 | 기본값 |
|---|---|---|
| `optional` (`@ManyToOne`만) | false면 연관 엔티티가 항상 있어야 함 | true |
| `mappedBy` (`@OneToMany`만) | 연관관계의 주인 필드 선택 | |
| `fetch` | 글로벌 페치 전략 | `@ManyToOne` = **EAGER**, `@OneToMany` = LAZY |
| `cascade` | 영속성 전이 | |
| `targetEntity` | 연관 엔티티 타입 (제네릭으로 알 수 있어 거의 안 씀) | |

- **`@ManyToOne`에는 `mappedBy`가 없다** → 다대일은 항상 주인이 된다는 뜻

---

## 면접 포인트

- **일대다 단방향을 피하는 이유?** FK가 상대 테이블에 있어 추가 UPDATE가 나가고, 엔티티와 실제 변경 테이블이 달라 운영이 헷갈림. 다대일 양방향으로 대체.
- **`@ManyToMany`를 실무에서 안 쓰는 이유?** 연결 테이블에 수량·시간 같은 컬럼을 추가할 수 없고 숨겨진 테이블로 예상 못 한 쿼리가 나감. 연결 엔티티로 승격해 1:N + N:1.
- **일대일에서 대상 테이블에 FK를 두면?** 1:N 전환에 유리하지만 프록시 한계로 지연 로딩이 안 되고 항상 즉시 로딩됨.
