## 한 줄 요약

**모든 연관관계는 지연 로딩(LAZY)** 으로 하고 필요한 곳만 페치 조인. 부모가 자식의 생명주기를 완전히 소유할 때만 `cascade = ALL` + `orphanRemoval = true`.

## 1. 프록시

Member를 조회할 때 Team도 함께 조회해야 할까? — 회원과 팀을 함께 출력하는 로직이면 같이, **회원만 출력하는 로직이면 Team 조회는 낭비**

### em.find() vs em.getReference()

| | 동작 |
|---|---|
| `em.find()` | DB를 통해 **실제 엔티티** 조회 |
| `em.getReference()` | DB 조회를 미루는 **가짜(프록시) 엔티티** 조회 |

### 프록시 특징

- **실제 클래스를 상속**받아 만들어짐 → 겉모양이 같아서 사용하는 쪽은 구분 없이 쓰면 됨(이론상)
- 실제 객체의 참조(`target`)를 보관하고, 호출되면 실제 객체의 메서드를 호출

### 프록시 객체의 초기화

```java
Member member = em.getReference(Member.class, "id1");
member.getName();
```

1. `getName()` 호출 → target이 비어 있음
2. 영속성 컨텍스트에 **초기화 요청**
3. 영속성 컨텍스트가 DB 조회
4. 실제 Entity 생성
5. `target.getName()` 호출

### 프록시의 특징 ★

- 처음 사용할 때 **한 번만** 초기화
- 초기화돼도 프록시가 실제 엔티티로 **바뀌는 게 아님**. 프록시를 통해 실제 엔티티에 접근할 뿐
- 원본 엔티티를 상속 → **타입 체크 시 `==` 비교 실패, `instanceof` 사용** (`getClass()` 비교 금지)
- 영속성 컨텍스트에 이미 실제 엔티티가 있으면 `getReference()`도 **실제 엔티티 반환** (반대로 프록시를 먼저 받았으면 이후 `find()`도 프록시 반환) → **같은 트랜잭션 안에서 `==` 보장**을 위해
- **준영속 상태에서 프록시를 초기화하면 문제** → 하이버네이트는 `org.hibernate.LazyInitializationException`
  - `em.detach()`, `em.close()`, `em.clear()` 후 초기화 시도. 실무에서 트랜잭션 끝난 뒤(예: 뷰/컨트롤러) 지연 로딩 시 자주 만남

### 프록시 확인 유틸

| 목적 | 방법 |
|---|---|
| 초기화 여부 | `emf.getPersistenceUnitUtil().isLoaded(entity)` |
| 프록시 클래스 확인 | `entity.getClass().getName()` → `...HibernateProxy...` |
| 강제 초기화 | `org.hibernate.Hibernate.initialize(entity)` (JPA 표준엔 없음 → `member.getName()` 처럼 호출) |

## 2. 즉시 로딩과 지연 로딩

### 지연 로딩 (LAZY) — 프록시로 조회

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "TEAM_ID")
private Team team;
```

```java
Member member = em.find(Member.class, 1L);  // MEMBER만 조회, team엔 프록시
Team team = member.getTeam();               // 아직 프록시
team.getName();                             // 실제 team을 사용하는 시점에 초기화 (DB 조회)
```

### 즉시 로딩 (EAGER) — 함께 조회

```java
@ManyToOne(fetch = FetchType.EAGER)
```

- Member 조회 시 항상 Team도 조회. JPA 구현체는 가능하면 **조인으로 SQL 한 번에** 조회 (프록시 X)

### 프록시와 즉시 로딩 주의 ★★

- **가급적 지연 로딩만 사용 (특히 실무에서)**
- 즉시 로딩은 **예상하지 못한 SQL** 발생 (테이블 10개가 엮이면 조인 10개)
- 즉시 로딩은 **JPQL에서 N+1 문제**를 일으킨다
  - `select m from Member m` → JPQL은 SQL로 그대로 번역돼 MEMBER만 조회 (1)
  - 그런데 team이 EAGER라 값이 있어야 하니 회원 수만큼 TEAM 조회 쿼리 추가 (N)
- **`@ManyToOne`, `@OneToOne`은 기본이 즉시 로딩 → LAZY로 설정**
- `@OneToMany`, `@ManyToMany`는 기본이 지연 로딩

### N+1 해결 (뒤에서 설명)

1. 일단 전부 LAZY
2. **JPQL 페치 조인** (`join fetch`) — 동적으로 필요한 것만 한 번에 ([10장](10_객체지향_쿼리_언어.md))
3. 엔티티 그래프 (`@EntityGraph`)
4. 배치 사이즈 (`@BatchSize`, `hibernate.default_batch_fetch_size`)

## 3. 지연 로딩 활용

- 이론상: Member–Team 자주 함께 → 즉시 / Member–Order 가끔 → 지연 / Order–Product 자주 → 즉시
- **실무 ★**
  - **모든 연관관계에 지연 로딩을 사용해라!**
  - **실무에서 즉시 로딩을 사용하지 마라!**
  - JPQL **fetch 조인**이나 **엔티티 그래프** 기능을 사용해라
  - 즉시 로딩은 상상하지 못한 쿼리가 나간다

## 4. 영속성 전이: CASCADE

- 특정 엔티티를 영속 상태로 만들 때 **연관된 엔티티도 함께** 영속 상태로 만들고 싶을 때
- 예: 부모 저장 시 자식도 함께 저장

```java
@OneToMany(mappedBy = "parent", cascade = CascadeType.PERSIST)
private List<Child> childList = new ArrayList<>();
```

```java
parent.addChild(child1);
parent.addChild(child2);
em.persist(parent);   // child1, child2도 함께 persist (원래는 3번 호출해야 함)
```

### 주의

- 영속성 전이는 **연관관계 매핑과 아무 관련 없음**. 영속화할 때 연관 엔티티도 함께 영속화하는 **편리함**만 제공

### CASCADE 종류

`ALL`(모두) · `PERSIST`(영속) · `REMOVE`(삭제) · `MERGE`(병합) · `REFRESH` · `DETACH` — 주로 **ALL, PERSIST**

### 언제 쓰나

- **단일 소유자**일 때만: 부모 하나만 자식을 관리하는 경우 (게시글–첨부파일). 자식이 다른 엔티티와도 연관되면 쓰면 안 됨
- 부모와 자식의 **라이프사이클이 거의 같을** 때

## 5. 고아 객체

- **부모와 연관관계가 끊어진 자식 엔티티를 자동 삭제**
- `orphanRemoval = true`

```java
Parent parent1 = em.find(Parent.class, id);
parent1.getChildren().remove(0);   // 컬렉션에서 제거
// → DELETE FROM CHILD WHERE ID = ?
```

### 주의

- 참조가 제거된 엔티티를 다른 곳에서 참조하지 않는 고아로 보고 삭제 → **참조하는 곳이 하나일 때만** 사용
- **특정 엔티티가 개인 소유**할 때
- `@OneToOne`, `@OneToMany`만 가능
- 참고: 부모를 제거하면 자식도 고아 → 부모 제거 시 자식도 함께 제거됨 (`CascadeType.REMOVE`처럼 동작)

---

## 6. 영속성 전이 + 고아 객체, 생명주기

- **`CascadeType.ALL + orphanRemoval = true`**
- 스스로 생명주기를 관리하는 엔티티는 `em.persist()`로 영속화, `em.remove()`로 제거
- 두 옵션을 모두 켜면 **부모 엔티티를 통해 자식의 생명주기를 관리** 가능 (자식 Repository가 필요 없어짐)
- DDD의 **Aggregate Root** 개념 구현에 유용

## 7. 실전 예제 5 — 연관관계 관리

- **글로벌 페치 전략**: 모든 연관관계를 지연 로딩으로. `@ManyToOne`, `@OneToOne`은 기본이 즉시 로딩이므로 LAZY로 변경
- **영속성 전이**
  - `Order → Delivery`: `cascade = ALL` (주문 저장 시 배송 정보도 함께)
  - `Order → OrderItem`: `cascade = ALL` (주문 저장 시 주문 상품도 함께)

## 면접 포인트

- **프록시란, 왜 쓰나?** 실제 엔티티를 상속한 가짜 객체로, 실제 사용 시점까지 DB 조회를 미뤄 지연 로딩을 구현.
- **LazyInitializationException은 언제?** 영속성 컨텍스트가 닫히거나 분리된(준영속) 뒤 프록시를 초기화할 때.
- **N+1 문제와 해결?** 즉시/지연 로딩 연관을 가진 엔티티 목록을 JPQL로 조회하면 결과 N개마다 추가 쿼리가 나감. 전부 LAZY로 두고 페치 조인, 엔티티 그래프, 배치 사이즈로 해결.
- **cascade와 orphanRemoval 차이?** cascade는 부모의 영속 작업(저장·삭제 등)을 자식에 전파, orphanRemoval은 부모와의 관계가 끊긴 자식을 삭제. 둘 다 단일 소유자일 때만.
