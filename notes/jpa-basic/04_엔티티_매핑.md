## 1. 객체와 테이블 매핑

### @Entity

- 붙은 클래스는 JPA가 관리 → **엔티티**. 테이블과 매핑하려면 필수
- **주의**
  - **기본 생성자 필수** (파라미터 없는 `public` 또는 `protected`) — JPA가 리플렉션·프록시로 객체를 만들기 때문
  - `final` 클래스, `enum`, `interface`, `inner` 클래스 사용 X
  - 저장할 필드에 `final` 사용 X
- 속성 `name`: JPA에서 쓸 엔티티 이름 (기본값 = 클래스 이름). 같은 이름 클래스가 없으면 기본값 사용

### @Table — 매핑할 테이블 지정

| 속성 | 기능 | 기본값 |
|---|---|---|
| `name` | 매핑할 테이블 이름 | 엔티티 이름 |
| `catalog`, `schema` | DB catalog / schema 매핑 | |
| `uniqueConstraints` (DDL) | DDL 생성 시 유니크 제약 조건 | |

## 2. 데이터베이스 스키마 자동 생성

- 애플리케이션 실행 시점에 **DDL 자동 생성** → 테이블 중심 → 객체 중심
- 방언을 활용해 DB에 맞는 DDL 생성 (예: H2 `varchar` / Oracle `varchar2`)
- 생성된 DDL은 **개발 장비에서만** 사용. 운영에선 안 쓰거나 다듬어서 사용

### `hibernate.hbm2ddl.auto`

| 옵션 | 설명 |
|---|---|
| `create` | 기존 테이블 삭제 후 다시 생성 (DROP + CREATE) |
| `create-drop` | create + 종료 시점에 DROP (테스트용) |
| `update` | 변경분만 반영 (컬럼 추가만, 삭제는 안 함) — 운영 DB 사용 금지 |
| `validate` | 엔티티와 테이블이 정상 매핑되었는지만 확인 |
| `none` | 사용 안 함 (사실 관례상 쓰는 값) |

> 참고: Spring Boot에서는 `spring.jpa.hibernate.ddl-auto`

### 주의 ★

- **운영 장비에는 절대 `create`, `create-drop`, `update` 사용 금지** (데이터 날아감, ALTER가 운영 중 락을 잡을 수 있음)
- 개발 초기: `create` 또는 `update`
- 테스트 서버: `update` 또는 `validate`
- 스테이징·운영: `validate` 또는 `none`

### DDL 생성 기능

```java
@Column(nullable = false, length = 10)   // 필수, 10자 초과 X
@Table(uniqueConstraints = {@UniqueConstraint(name = "NAME_AGE_UNIQUE", columnNames = {"NAME", "AGE"})})
```

- **DDL을 자동 생성할 때만** 사용되고 JPA 실행 로직에는 영향 X

## 3. 필드와 컬럼 매핑

요구사항: 일반 회원/관리자 구분, 가입일·수정일, 길이 제한 없는 설명 필드

```java
@Entity
public class Member {
    @Id
    private Long id;

    @Column(name = "name")              // 객체는 username, 컬럼은 name
    private String username;

    private Integer age;                // Integer → DB 숫자 타입

    @Enumerated(EnumType.STRING)        // enum
    private RoleType roleType;

    @Temporal(TemporalType.TIMESTAMP)   // 날짜
    private Date createdDate;

    @Temporal(TemporalType.TIMESTAMP)
    private Date lastModifiedDate;

    @Lob                                // 큰 문자 → CLOB
    private String description;

    @Transient                          // 매핑 X
    private int temp;
}
```

### 매핑 어노테이션 정리

| 어노테이션 | 설명 |
|---|---|
| `@Column` | 컬럼 매핑 |
| `@Temporal` | 날짜 타입 매핑 |
| `@Enumerated` | enum 타입 매핑 |
| `@Lob` | BLOB, CLOB 매핑 |
| `@Transient` | 특정 필드를 컬럼에 매핑하지 않음 (DB 저장·조회 X, 메모리에서만 임시 보관) |

### @Column 속성

| 속성 | 설명 | 기본값 |
|---|---|---|
| `name` | 매핑할 컬럼 이름 | 필드 이름 |
| `insertable`, `updatable` | 등록·변경 가능 여부 | true |
| `nullable` (DDL) | false면 `not null` 제약 | |
| `unique` (DDL) | 한 컬럼에 유니크 제약 (제약 이름이 랜덤으로 생겨서 실무에선 `@Table(uniqueConstraints)` 선호) | |
| `columnDefinition` (DDL) | 컬럼 정보 직접 지정 `varchar(100) default 'EMPTY'` | 자바 타입 + 방언으로 결정 |
| `length` (DDL) | 문자 길이, String에만 | 255 |
| `precision`, `scale` (DDL) | BigDecimal/BigInteger용 전체 자릿수 / 소수 자릿수 (double·float엔 적용 X) | 19, 2 |

### @Enumerated — **ORDINAL 사용 X**

| 값 | 저장 내용 |
|---|---|
| `EnumType.ORDINAL` (기본값) | enum **순서**(0, 1, 2…) |
| `EnumType.STRING` | enum **이름** ("USER", "ADMIN") |

- ORDINAL은 enum 중간에 값이 추가되면 기존 데이터의 의미가 꼬임 → **무조건 STRING**

### @Temporal

- `java.util.Date`, `Calendar` 매핑용: `DATE`(날짜) / `TIME`(시간) / `TIMESTAMP`(날짜+시간)
- **`LocalDate`, `LocalDateTime`을 쓰면 생략 가능** (최신 하이버네이트 지원) → 요즘은 그냥 `LocalDateTime` 쓰면 됨

### @Lob

- 속성 없음. 필드 타입이 **문자면 CLOB**(`String`, `char[]`, `java.sql.Clob`), **나머지는 BLOB**(`byte[]`, `java.sql.Blob`)

## 4. 기본 키 매핑

```java
@Id @GeneratedValue(strategy = GenerationType.AUTO)
private Long id;
```

| 방법 | 설명 |
|---|---|
| 직접 할당 | `@Id`만 사용 |
| `IDENTITY` | DB에 위임 (MySQL) |
| `SEQUENCE` | DB 시퀀스 오브젝트 사용 (Oracle), `@SequenceGenerator` |
| `TABLE` | 키 생성용 테이블 사용, 모든 DB 가능, `@TableGenerator` |
| `AUTO` | 방언에 따라 자동 지정 (기본값) |

### IDENTITY 전략

- 기본 키 생성을 DB에 위임 (MySQL `AUTO_INCREMENT`, PostgreSQL, SQL Server, DB2)
- 문제: JPA는 보통 **커밋 시점**에 INSERT하는데, AUTO_INCREMENT는 **INSERT 해봐야** ID를 알 수 있음
  → 영속성 컨텍스트에 넣으려면 PK가 있어야 하므로
- **IDENTITY 전략은 `em.persist()` 시점에 즉시 INSERT 실행**하고 DB에서 식별자를 조회 (JDBC가 생성된 키를 돌려줌)
- 그래서 IDENTITY에선 INSERT 쓰기 지연(배치)이 안 됨 — 실무에서 크게 문제 되진 않음

```java
@Id @GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

### SEQUENCE 전략

- DB 시퀀스 = 유일한 값을 순서대로 생성하는 DB 오브젝트 (Oracle, PostgreSQL, DB2, H2)

```java
@Entity
@SequenceGenerator(
    name = "MEMBER_SEQ_GENERATOR",
    sequenceName = "MEMBER_SEQ",          // 매핑할 DB 시퀀스 이름
    initialValue = 1, allocationSize = 1)
public class Member {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "MEMBER_SEQ_GENERATOR")
    private Long id;
}
```

| 속성 | 설명 | 기본값 |
|---|---|---|
| `name` | 식별자 생성기 이름 | 필수 |
| `sequenceName` | DB 시퀀스 이름 | hibernate_sequence |
| `initialValue` | DDL 생성 시 시작 값 | 1 |
| `allocationSize` | 시퀀스 한 번 호출에 증가하는 수 (성능 최적화) | **50** |

- `persist()` 시점에 `call next value for MEMBER_SEQ`로 PK만 받아오고, INSERT는 커밋 때 → **쓰기 지연 가능**
- **최적화 (allocationSize = 50)**: 시퀀스를 한 번 호출할 때 50개를 미리 확보해 메모리에서 하나씩 사용 → 네트워크 왕복 감소
  - 처음엔 DB 시퀀스를 2번 호출(1, 51) → 이후 1~50은 메모리에서, 51에 도달하면 다시 호출
  - 여러 서버가 동시에 써도 시퀀스가 미리 올라가 있어 충돌 X
  - DB 시퀀스가 1씩 증가하도록 이미 만들어져 있다면 **반드시 1로 맞춰야** 함

### TABLE 전략

- 키 생성 전용 테이블로 시퀀스를 흉내 → 장점: 모든 DB 적용 / **단점: 성능** (락, 테이블 조회)
- `@TableGenerator(name, table = "MY_SEQUENCES", pkColumnValue = "MEMBER_SEQ", allocationSize = 1)`
- 실무에선 잘 안 씀 (DB 표준 시퀀스/IDENTITY를 쓰면 됨)

### 권장하는 식별자 전략 ★

- 기본 키 제약: **null 아님, 유일, 변하면 안 됨**
- 미래까지 이걸 만족하는 **자연키**(주민번호, 전화번호…)는 찾기 어렵다 → **대리키(대체키)** 사용
- 주민등록번호도 기본 키로 부적절 (정책 변경으로 저장 불가해지면 FK로 물린 모든 테이블이 영향)
- **권장: `Long`형 + 대체키 + 키 생성 전략**
  - `int`는 21억에서 끝남, `Long`이 안전

## 5. 실전 예제 1 — 요구사항 분석과 기본 매핑

- 회원은 상품을 주문할 수 있고, 주문 시 여러 종류의 상품을 선택할 수 있다
- 기능: 회원(등록·조회), 상품(등록·수정·조회), 주문(상품 주문·주문 내역 조회·주문 취소)
- 도메인 모델
  - 회원 : 주문 = 1 : N
  - 주문 : 상품 = N : M → **주문상품(OrderItem)** 으로 풀어서 1:N, N:1

```
MEMBER (MEMBER_ID, NAME, CITY, STREET, ZIPCODE)
ORDERS (ORDER_ID, MEMBER_ID(FK), ORDERDATE, STATUS)          ← ORDER는 예약어라 ORDERS
ORDER_ITEM (ORDER_ITEM_ID, ORDER_ID(FK), ITEM_ID(FK), ORDERPRICE, COUNT)
ITEM (ITEM_ID, NAME, PRICE, STOCKQUANTITY)
```

### 데이터 중심 설계의 문제점

- 지금은 엔티티에 `Long memberId` 같은 **외래 키를 그대로** 가져옴 = 객체 설계를 테이블 설계에 맞춘 것
- `order.getMemberId()`로 다시 `em.find()` 해야 함 → **객체 그래프 탐색 불가**, 참조가 없으니 UML도 잘못됨
- → [5장](05_연관관계_매핑_기초.md)에서 참조로 바꾼다

> 참고(강의 팁): 컬럼명은 `@Column(name = "ORDER_ID")`처럼 명시하거나 스프링 부트의 기본 네이밍 전략(카멜 → 스네이크)을 활용. 엔티티에 setter를 무분별하게 열지 말 것.

## 면접 포인트

- **운영에서 ddl-auto는?** `validate` 또는 `none`. create/update는 데이터 손실·락 위험.
- **`@Enumerated` 기본값의 문제?** 기본값 ORDINAL은 순서를 저장해서 enum 순서가 바뀌면 데이터가 깨짐 → STRING.
- **IDENTITY 전략에서 쓰기 지연이 안 되는 이유?** ID를 INSERT 후에야 알 수 있는데 영속성 컨텍스트는 PK로 엔티티를 관리하므로 persist 시점에 바로 INSERT해야 함.
- **SEQUENCE allocationSize의 역할?** 시퀀스 값을 미리 여러 개 확보해 메모리에서 쓰는 최적화, DB 왕복을 줄임.
