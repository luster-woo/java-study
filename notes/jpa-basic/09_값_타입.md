## 한 줄 요약

값 타입은 **식별자가 없고 엔티티에 생명주기를 의존**한다. 공유하면 위험하므로 **불변 객체**로 만들고, `equals()`로 비교한다.

---

## 1. JPA의 데이터 타입 분류

| | 엔티티 타입 | 값 타입 |
|---|---|---|
| 정의 | `@Entity`로 정의하는 객체 | `int`, `Integer`, `String`처럼 단순히 값으로 쓰는 자바 기본 타입이나 객체 |
| 식별자 | 있음 → 데이터가 변해도 **추적 가능** | 없음 → 변경 시 추적 불가 (100을 200으로 바꾸면 완전히 다른 값) |

### 값 타입 분류

1. **기본값 타입**: 자바 기본 타입(`int`, `double`), 래퍼 클래스(`Integer`, `Long`), `String`
2. **임베디드 타입** (embedded type, 복합 값 타입)
3. **컬렉션 값 타입** (collection value type)

---

## 2. 기본값 타입

- 생명주기를 **엔티티에 의존** (회원 삭제 시 이름·나이 필드도 삭제)
- 값 타입은 **공유하면 X** (회원 이름 변경 시 다른 회원 이름도 바뀌면 안 됨)
- 참고: 자바의 기본 타입(primitive)은 **절대 공유 X, 항상 값을 복사**. `Integer` 같은 래퍼나 `String`은 공유 가능한 객체지만 **변경 X**

---

## 3. 임베디드 타입 (복합 값 타입)

- 새로운 값 타입을 직접 정의. 주로 기본 값 타입을 모아서 만들어 **복합 값 타입**이라고도 함 (그래도 `int`, `String`과 같은 **값 타입**)

```
Member(id, name, startDate, endDate, city, street, zipcode)
   ↓ 묶기
Member(id, name, workPeriod: Period, homeAddress: Address)
```

### 사용법

- `@Embeddable`: 값 타입을 **정의하는 곳**
- `@Embedded`: 값 타입을 **사용하는 곳**
- **기본 생성자 필수**

```java
@Embeddable
public class Address {
    private String city;
    private String street;
    private String zipcode;

    protected Address() {}                       // JPA용
    public Address(String city, String street, String zipcode) { ... }
    // getter만, setter X (불변)
}

@Entity
public class Member {
    @Id @GeneratedValue
    private Long id;
    private String name;

    @Embedded
    private Period workPeriod;
    @Embedded
    private Address homeAddress;
}
```

### 장점

- **재사용**, **높은 응집도**
- `Period.isWork()`처럼 해당 값 타입만 쓰는 **의미 있는 메서드** 작성 가능
- 임베디드 타입을 포함한 모든 값 타입은 소유한 엔티티에 **생명주기 의존**

### 테이블 매핑

- 임베디드 타입은 **엔티티의 값일 뿐** → 사용 전과 후에 **매핑하는 테이블은 같다**
- 객체와 테이블을 아주 세밀하게(fine-grained) 매핑 가능
- 잘 설계한 ORM 애플리케이션은 **매핑한 테이블 수보다 클래스 수가 더 많음**
- 임베디드 타입이 엔티티를 가질 수도 있음 (`Address` 안에 `@ManyToOne PhoneEntity`, FK만 있으면 됨)

### @AttributeOverride — 속성 재정의

- 한 엔티티에서 같은 값 타입을 두 번 쓰면(집 주소, 회사 주소) **컬럼명 중복**

```java
@Embedded
@AttributeOverrides({
    @AttributeOverride(name = "city",    column = @Column(name = "WORK_CITY")),
    @AttributeOverride(name = "street",  column = @Column(name = "WORK_STREET")),
    @AttributeOverride(name = "zipcode", column = @Column(name = "WORK_ZIPCODE"))
})
private Address workAddress;
```

### 임베디드 타입과 null

- 임베디드 타입 값이 null이면 매핑한 컬럼 값은 **모두 null**

## 4. 값 타입과 불변 객체

> 값 타입은 복잡한 객체 세상을 조금이라도 단순화하려고 만든 개념 → **단순하고 안전하게** 다룰 수 있어야 함

### 값 타입 공유 참조 — 부작용

```java
Address address = new Address("city", "street", "10000");
member1.setHomeAddress(address);
member2.setHomeAddress(address);          // 같은 인스턴스 공유
member1.getHomeAddress().setCity("newCity");
// → member1, member2 둘 다 UPDATE 쿼리 나감 (side effect)
```

- 대신 **값(인스턴스)을 복사**해서 사용 → `new Address(address.getCity(), ...)`

### 객체 타입의 한계

- 기본 타입은 대입하면 **값을 복사** (`int b = a; b = 4;` → a는 그대로)
- 임베디드 타입은 **객체 타입** → 대입하면 **참조를 전달** (`Address b = a; b.setCity("New")` → a도 바뀜)
- 참조 값을 직접 대입하는 걸 **막을 방법이 없음** → 공유 참조는 피할 수 없다

### 불변 객체 ★

- 객체 타입을 **수정할 수 없게** 만들면 부작용 원천 차단 → **값 타입은 불변 객체로 설계**
- 생성 시점 이후 절대 값을 변경할 수 없는 객체
- **생성자로만 값을 설정하고 setter를 만들지 않으면 됨** (또는 private setter)
- 값을 바꾸고 싶으면 **새로 만들어서 통째로 교체**: `member.setHomeAddress(new Address("newCity", ...))`
- 참고: `Integer`, `String`은 자바가 제공하는 대표적인 불변 객체

> **불변이라는 작은 제약으로 부작용이라는 큰 재앙을 막을 수 있다.**

> 참고: Java 16+의 `record`는 불변 값 객체지만, JPA 임베디드 타입으로 쓰려면 Hibernate 6.2+가 필요하다. 강의 방식(불변 클래스)으로 해도 충분하다.

## 5. 값 타입의 비교

- 값 타입은 **인스턴스가 달라도 안의 값이 같으면 같은 것**으로 봐야 함

| 비교 | 의미 | 사용 |
|---|---|---|
| **동일성(identity)** | 인스턴스 참조 값 비교 | `==` |
| **동등성(equivalence)** | 인스턴스의 값 비교 | `equals()` |

- 값 타입은 `a.equals(b)`로 **동등성 비교**
- 값 타입의 **`equals()`를 적절히 재정의** (주로 모든 필드 사용) + `hashCode()`도 함께 (컬렉션에서 필요)
  - 강의 팁: IntelliJ 자동 생성 시 **getter 사용 옵션**을 켜야 프록시일 때도 안전

---

## 6. 값 타입 컬렉션

- 값 타입을 **하나 이상** 저장할 때
- `@ElementCollection`, `@CollectionTable`
- DB는 컬렉션을 같은 테이블에 저장할 수 없음 → **별도 테이블** 필요

```java
@ElementCollection
@CollectionTable(name = "FAVORITE_FOOD", joinColumns = @JoinColumn(name = "MEMBER_ID"))
@Column(name = "FOOD_NAME")
private Set<String> favoriteFoods = new HashSet<>();

@ElementCollection
@CollectionTable(name = "ADDRESS", joinColumns = @JoinColumn(name = "MEMBER_ID"))
private List<Address> addressHistory = new ArrayList<>();
```

### 사용

- 저장: 멤버만 persist해도 컬렉션까지 저장 (생명주기를 엔티티에 의존)
- 조회: 값 타입 컬렉션도 **지연 로딩**
- 수정: 값 타입이니 **통째로 교체** (`remove(old)` 후 `add(new)`, String은 `remove("치킨")`, `add("한식")`) — 컬렉션에서 지울 때 `equals()`가 쓰이므로 재정의 필수
- 참고: 값 타입 컬렉션은 **영속성 전이(Cascade) + 고아 객체 제거**를 필수로 가진다고 볼 수 있다

### 제약사항

- 값 타입은 엔티티와 달리 **식별자 개념이 없다** → 변경하면 추적이 어렵다
- 변경 사항이 생기면 **주인 엔티티와 연관된 모든 데이터를 삭제하고, 현재 값을 모두 다시 저장** (DELETE 1번 + INSERT N번)
- 매핑 테이블은 **모든 컬럼을 묶어서 기본 키** 구성 → null 입력 X, 중복 저장 X

### 대안 — 실무

- 상황에 따라 값 타입 컬렉션 대신 **일대다 관계** 고려
- 일대다용 엔티티(`AddressEntity`)를 만들고 그 안에서 값 타입 사용
- **영속성 전이(Cascade) + 고아 객체 제거**로 값 타입 컬렉션처럼 사용

```java
@OneToMany(cascade = CascadeType.ALL, orphanRemoval = true)
@JoinColumn(name = "MEMBER_ID")
private List<AddressEntity> addressHistory = new ArrayList<>();
```

- 값 타입 컬렉션은 "좋아하는 메뉴 체크박스"처럼 **정말 단순하고 추적할 필요 없을 때만**

## 7. 정리

| 엔티티 타입 | 값 타입 |
|---|---|
| 식별자 O | 식별자 X |
| 생명 주기 관리 | 생명 주기를 엔티티에 의존 |
| 공유 | 공유하지 않는 것이 안전 (복사해서 사용), **불변 객체**로 만드는 것이 안전 |

- 값 타입은 **정말 값 타입이라 판단될 때만** 사용
- 엔티티를 값 타입으로 만들면 안 됨 — **식별자가 필요하고 지속해서 값을 추적·변경해야 한다면 엔티티**

### 실전 예제 6 — 값 타입 매핑

- `Address`(city, street, zipcode)를 `@Embeddable`로 만들어 `Member`와 `Delivery`에서 `@Embedded`로 사용
- `Address`에 `fullAddress()` 같은 의미 있는 메서드, `@Column(length = 10)` 같은 제약도 한곳에서 관리

## 면접 포인트

- **엔티티 vs 값 타입?** 식별자로 추적 가능하고 독립 생명주기를 가지면 엔티티, 식별자 없이 엔티티에 종속된 값이면 값 타입.
- **값 타입을 불변으로 만드는 이유?** 임베디드 타입은 객체라 대입 시 참조가 공유되고, 한쪽 수정이 다른 엔티티까지 바꾸는 부작용이 생김. setter를 없애 원천 차단.
- **값 타입 컬렉션을 실무에서 조심하는 이유?** 식별자가 없어 변경 시 전체 삭제 후 재삽입, 모든 컬럼이 PK라 null·중복 불가. 대신 일대다 엔티티 + cascade + orphanRemoval.
