## 한 줄 요약

JPQL은 **엔티티 대상 객체지향 SQL**. 실무 성능 문제의 대부분은 **페치 조인**으로 해결하고, 동적 쿼리는 QueryDSL, 화면용 조회는 DTO로.

---

## 1. JPA가 지원하는 쿼리 방법

| 방법 | 특징 |
|---|---|
| **JPQL** | 표준, 문자열 쿼리 — 기본 |
| JPA Criteria | 자바 코드로 JPQL 작성(JPQL 빌더), JPA 공식. **너무 복잡하고 실용성 없음** |
| **QueryDSL** | 자바 코드로 JPQL 작성, **컴파일 시점 문법 오류 검출**, 동적 쿼리 편리, 단순·쉬움 → **실무 사용 권장** |
| 네이티브 SQL | `em.createNativeQuery()`. JPQL로 안 되는 DB 의존 기능(오라클 `CONNECT BY`, SQL 힌트) |
| JDBC 직접, JdbcTemplate, MyBatis | 함께 사용 가능. 단 **JPA를 우회하는 SQL 실행 직전에 영속성 컨텍스트 수동 flush** 필요 |

> 실무: **JPQL + QueryDSL**로 95% 해결, 나머지는 네이티브 SQL·JdbcTemplate

```java
// QueryDSL 맛보기
JPAQueryFactory query = new JPAQueryFactory(em);
QMember m = QMember.member;
List<Member> list = query.selectFrom(m)
        .where(m.age.gt(18))
        .orderBy(m.name.desc())
        .fetch();
```

## 2. JPQL 기본 문법

- 테이블이 아닌 **엔티티 객체 대상** 쿼리, SQL을 추상화해 특정 DB에 의존 X, **결국 SQL로 변환**됨

```
select_문 ::= select_절 from_절 [where_절] [groupby_절] [having_절] [orderby_절]
update_문 ::= update_절 [where_절]
delete_문 ::= delete_절 [where_절]
```

`select m from Member as m where m.age > 18`
- **엔티티와 속성은 대소문자 구분 O** (`Member`, `age`)
- **JPQL 키워드는 구분 X** (`SELECT`, `from`)
- 테이블 이름이 아닌 **엔티티 이름** 사용
- **별칭 필수** (`as`는 생략 가능)

### 집합과 정렬

`COUNT(m)`, `SUM(m.age)`, `AVG`, `MAX`, `MIN` / `GROUP BY`, `HAVING`, `ORDER BY` — SQL과 같음

### TypedQuery, Query

```java
TypedQuery<Member> q1 = em.createQuery("SELECT m FROM Member m", Member.class); // 반환 타입 명확
Query q2 = em.createQuery("SELECT m.username, m.age FROM Member m");            // 불명확
```

### 결과 조회 API

| 메서드 | 결과 |
|---|---|
| `getResultList()` | 하나 이상 → 리스트. **없으면 빈 리스트** |
| `getSingleResult()` | 정확히 하나. **없으면 `NoResultException`**, 둘 이상이면 `NonUniqueResultException` |

> 참고: Spring Data JPA는 단건 조회 결과가 없으면 예외 대신 `null`/`Optional`로 감싸준다.

### 파라미터 바인딩

```java
em.createQuery("SELECT m FROM Member m where m.username = :username", Member.class)
  .setParameter("username", "member1")   // 이름 기준 — 이걸 쓰자
  .getSingleResult();
// 위치 기준 ?1 은 순서가 바뀌면 버그 → 쓰지 말 것
```

## 3. 프로젝션 (SELECT 절에 조회할 대상)

| 대상 | 예 |
|---|---|
| 엔티티 | `SELECT m FROM Member m`, `SELECT m.team FROM Member m` (→ 조인이 나가니 명시적 join 권장) |
| 임베디드 타입 | `SELECT m.address FROM Member m` |
| 스칼라 타입 | `SELECT m.username, m.age FROM Member m` |

- `DISTINCT`로 중복 제거
- **엔티티 프로젝션으로 조회한 엔티티는 모두 영속성 컨텍스트에서 관리됨**

### 여러 값 조회

1. `Query` 타입으로 조회
2. `Object[]` 타입으로 조회
3. **`new` 명령어로 DTO 바로 조회** ← 제일 깔끔

```java
List<MemberDTO> result = em.createQuery(
        "select new jpql.MemberDTO(m.username, m.age) from Member m", MemberDTO.class)
        .getResultList();
```
- **패키지명 포함 전체 클래스명**, **순서와 타입이 일치하는 생성자** 필요 (QueryDSL 쓰면 편해짐)

## 4. 페이징 API

- `setFirstResult(int startPosition)`: 시작 위치 (**0부터**)
- `setMaxResults(int maxResult)`: 개수

```java
em.createQuery("select m from Member m order by m.name desc", Member.class)
  .setFirstResult(10)
  .setMaxResults(20)
  .getResultList();
```

- 방언에 따라 MySQL은 `LIMIT ?, ?`, Oracle은 `ROWNUM` 3중 서브쿼리로 자동 변환

## 5. 조인

| 종류 | JPQL |
|---|---|
| 내부 조인 | `SELECT m FROM Member m [INNER] JOIN m.team t` |
| 외부 조인 | `SELECT m FROM Member m LEFT [OUTER] JOIN m.team t` |
| 세타 조인 | `select count(m) from Member m, Team t where m.username = t.name` (연관 없는 막조인, 내부 조인만) |

### ON 절 (JPA 2.1+)

1. **조인 대상 필터링**: `SELECT m, t FROM Member m LEFT JOIN m.team t on t.name = 'A'`
   → SQL: `... LEFT JOIN Team t ON m.TEAM_ID = t.id and t.name = 'A'`
2. **연관관계 없는 엔티티 외부 조인** (하이버네이트 5.1+): `SELECT m, t FROM Member m LEFT JOIN Team t on m.username = t.name`

## 6. 서브 쿼리

```sql
-- 나이가 평균보다 많은 회원
select m from Member m where m.age > (select avg(m2.age) from Member m2)
-- 한 건이라도 주문한 고객
select m from Member m where (select count(o) from Order o where m = o.member) > 0
```

지원 함수
- `[NOT] EXISTS (subquery)`
- `{ALL | ANY | SOME} (subquery)` — ALL: 모두 만족, ANY=SOME: 하나라도 만족
- `[NOT] IN (subquery)`

```sql
select m from Member m where exists (select t from m.team t where t.name = '팀A')
select o from Order o where o.orderAmount > ALL (select p.stockAmount from Product p)
select m from Member m where m.team = ANY (select t from Team t)
```

### 한계

- JPA 표준은 **WHERE, HAVING** 절에서만. SELECT 절은 하이버네이트 지원
- FROM 절 서브쿼리는 JPQL에서 불가 → 조인으로 풀거나, 네이티브 쿼리, 쿼리 2번
- **하이버네이트 6부터 FROM 절 서브쿼리 지원** ★ (2024 자료 추가 사항)

## 7. JPQL 타입 표현과 기타 식

- 문자 `'HELLO'`, `'She''s'` / 숫자 `10L`, `10D`, `10F` / Boolean `TRUE`, `FALSE`
- ENUM: `jpabook.MemberType.Admin` (**패키지명 포함**, 파라미터 바인딩 쓰면 편함)
- 엔티티 타입: `TYPE(m) = Member` (상속 관계)
- SQL과 같은 식: `EXISTS`, `IN`, `AND/OR/NOT`, `= > >= < <= <>`, `BETWEEN`, `LIKE`, `IS NULL`

### 조건식 — CASE

```sql
-- 기본 CASE
select case when m.age <= 10 then '학생요금'
            when m.age >= 60 then '경로요금'
            else '일반요금' end
from Member m
-- 단순 CASE
select case t.name when '팀A' then '인센티브110%' when '팀B' then '인센티브120%' else '인센티브105%' end
from Team t
```

- `COALESCE(m.username, '이름 없는 회원')`: 하나씩 조회해서 null이 아니면 반환
- `NULLIF(m.username, '관리자')`: 두 값이 같으면 null, 다르면 첫 번째 값

### 기본 함수

`CONCAT`, `SUBSTRING`, `TRIM`, `LOWER`, `UPPER`, `LENGTH`, `LOCATE`, `ABS`, `SQRT`, `MOD`, `SIZE`(컬렉션 크기), `INDEX`(JPA 용도)

### 사용자 정의 함수

- 하이버네이트는 사용 전 **방언에 추가**: 사용하는 DB 방언을 상속받고 함수 등록
- `select function('group_concat', i.name) from Item i`

## 8. 경로 표현식

`.`(점)을 찍어 객체 그래프를 탐색

```sql
select m.username        -- 상태 필드
from Member m
  join m.team t          -- 단일 값 연관 필드
  join m.orders o        -- 컬렉션 값 연관 필드
where t.name = '팀A'
```

| 종류 | 대상 | 특징 |
|---|---|---|
| **상태 필드** | 단순 값 (`m.username`) | **경로 탐색의 끝**, 더 탐색 X |
| **단일 값 연관 필드** | `@ManyToOne`, `@OneToOne` → 엔티티 (`m.team`) | **묵시적 내부 조인** 발생, 계속 탐색 O |
| **컬렉션 값 연관 필드** | `@OneToMany`, `@ManyToMany` → 컬렉션 (`m.orders`) | 묵시적 내부 조인 발생, **탐색 X** → FROM 절 명시적 조인으로 별칭 얻어서 탐색 |

예제

```sql
select o.member.team from Order o                -- 성공 (조인 2번)
select t.members from Team t                      -- 성공
select t.members.username from Team t             -- 실패 (컬렉션에서 더 탐색 불가)
select m.username from Team t join t.members m    -- 성공 (명시적 조인으로 별칭)
```

### 명시적 조인 vs 묵시적 조인

- 명시적: `join` 키워드 직접 사용 — `select m from Member m join m.team t`
- 묵시적: 경로 표현식에 의해 SQL 조인 발생 (**내부 조인만**) — `select m.team from Member m`
- 주의: 항상 내부 조인 / 컬렉션은 경로 탐색의 끝 / SELECT·WHERE에서 썼는데 SQL FROM(JOIN)에 영향

### 실무 조언 ★

- **가급적 묵시적 조인 대신 명시적 조인**
- 조인은 SQL 튜닝의 중요 포인트인데, 묵시적 조인은 조인이 일어나는 상황을 한눈에 파악하기 어려움

## 9. 페치 조인 (fetch join) ★★★ — 실무에서 정말정말 중요

- SQL 조인 종류 X. **JPQL에서 성능 최적화를 위해 제공하는 기능**
- **연관된 엔티티나 컬렉션을 SQL 한 번에 함께 조회**
- `[LEFT [OUTER] | INNER] JOIN FETCH 조인경로`

### 엔티티 페치 조인 (N:1)

```sql
-- JPQL
select m from Member m join fetch m.team
-- SQL
SELECT M.*, T.* FROM MEMBER M INNER JOIN TEAM T ON M.TEAM_ID = T.ID
```

```java
List<Member> members = em.createQuery("select m from Member m join fetch m.team", Member.class)
        .getResultList();
for (Member member : members) {
    // 페치 조인으로 회원과 팀을 함께 조회 → 지연 로딩 X, 프록시 X (진짜 Team)
    System.out.println(member.getUsername() + ", " + member.getTeam().getName());
}
```

- 페치 조인 없이 LAZY로 돌리면: 회원 조회 1번 + 팀마다 1번 = **N+1** (같은 팀은 1차 캐시 덕에 생략)

### 컬렉션 페치 조인 (1:N)

```sql
select t from Team t join fetch t.members where t.name = '팀A'
-- SQL
SELECT T.*, M.* FROM TEAM T INNER JOIN MEMBER M ON T.ID = M.TEAM_ID WHERE T.NAME = '팀A'
```

- 일대다 조인은 **데이터가 뻥튀기**됨: 팀A에 회원이 2명이면 결과 row 2개 → `teams` 리스트에 **같은 Team@0x100이 2번** 들어감

### 페치 조인과 DISTINCT

- SQL의 DISTINCT는 row가 완전히 같아야 제거 → 회원이 달라서 **SQL 결과에선 중복 제거 실패**
- JPQL의 DISTINCT는 2가지 기능
  1. SQL에 DISTINCT 추가
  2. **애플리케이션에서 같은 식별자를 가진 엔티티 중복 제거**
- **하이버네이트 6부터는 DISTINCT 없이도 애플리케이션 중복 제거가 자동 적용** ★ (Spring Boot 3)

### 페치 조인 vs 일반 조인

- 일반 조인: **연관 엔티티를 함께 조회하지 않음**. JPQL은 결과 반환 시 연관관계 고려 X, SELECT 절에 지정한 엔티티만 조회
  - `select t from Team t join t.members m` → SQL은 `SELECT T.*`만 (members는 LAZY 그대로)
- **페치 조인을 쓸 때만 연관 엔티티도 함께 조회 (즉시 로딩)**
- 페치 조인은 **객체 그래프를 SQL 한 번에 조회**하는 개념

### 페치 조인의 특징과 한계 ★

- **페치 조인 대상에는 별칭을 줄 수 없다** (하이버네이트는 가능하지만 가급적 X)
  - `join fetch t.members m where m.age > 10` 처럼 걸러내면 컬렉션 일부만 담긴 Team이 만들어져 객체 그래프 정합성이 깨짐. 페치 조인은 "연관된 걸 **전부** 가져온다"는 전제
- **둘 이상의 컬렉션은 페치 조인할 수 없다** (곱하기로 뻥튀기)
- **컬렉션 페치 조인하면 페이징 API(`setFirstResult`, `setMaxResults`) 사용 불가**
  - 일대일·다대일 같은 단일 값 연관은 페치 조인해도 페이징 가능
  - 하이버네이트는 **경고 로그를 남기고 메모리에서 페이징** (데이터 전부 퍼올림 → 매우 위험)

컬렉션 + 페이징 해결책 (강의 실습)
1. 방향을 뒤집기: `select m from Member m join fetch m.team` (다대일로 페이징)
2. 페치 조인 빼고 **`@BatchSize`** 사용

```java
@BatchSize(size = 100)
@OneToMany(mappedBy = "team")
private List<Member> members = new ArrayList<>();
```
   또는 글로벌 설정 `hibernate.default_batch_fetch_size = 100` (Spring Boot: `spring.jpa.properties.hibernate.default_batch_fetch_size`)
   → 팀 N개의 members를 `WHERE TEAM_ID IN (?, ?, ...)`으로 한 번에 → **N+1이 1+1**로

### 정리

- 연관 엔티티들을 SQL 한 번으로 조회 → **성능 최적화**
- 엔티티에 직접 적용하는 **글로벌 로딩 전략보다 우선**
- **실무에서 글로벌 로딩 전략은 모두 지연 로딩, 최적화가 필요한 곳만 페치 조인**
- 모든 걸 페치 조인으로 해결할 수는 없음 → 페치 조인은 **객체 그래프를 유지할 때** 효과적
- 여러 테이블을 조인해 엔티티 모양이 아닌 **전혀 다른 결과**가 필요하면 → 일반 조인 + 필요한 데이터만 **DTO**로 반환

> 성능 최적화 3단계: ① 엔티티 페치 조인으로 조회 → ② 페치 조인 후 애플리케이션에서 DTO 변환 → ③ JPQL에서 바로 DTO 조회 (`new`)

## 10. 다형성 쿼리

- **TYPE**: 조회 대상을 특정 자식으로 한정

```sql
select i from Item i where type(i) IN (Book, Movie)
-- SQL: select i from i where i.DTYPE in ('B', 'M')
```

- **TREAT** (JPA 2.1): 자바 타입 캐스팅과 유사, 부모를 특정 자식 타입으로. FROM, WHERE, SELECT(하이버네이트)

```sql
select i from Item i where treat(i as Book).author = 'kim'
-- SQL(단일 테이블): select i.* from Item i where i.DTYPE = 'B' and i.author = 'kim'
```

## 11. 엔티티 직접 사용

- JPQL에서 엔티티를 직접 사용하면 SQL에서 해당 엔티티의 **기본 키 값** 사용

```sql
select count(m.id) from Member m   -- 아이디 사용
select count(m) from Member m      -- 엔티티 직접 사용
-- 둘 다 SQL: select count(m.id) as cnt from Member m
```

```java
// 파라미터로 엔티티를 넘겨도, 식별자를 넘겨도 같은 SQL
.where m = :member      .setParameter("member", member)
.where m.id = :memberId .setParameter("memberId", memberId)
// SQL: select m.* from Member m where m.id = ?
```

- **외래 키 값**도 마찬가지: `where m.team = :team` == `where m.team.id = :teamId` → `where m.team_id = ?`

## 12. Named 쿼리

- 미리 정의해 이름을 붙여두고 쓰는 **정적 쿼리**, 어노테이션 또는 XML에 정의
- **애플리케이션 로딩 시점에 초기화 후 재사용** (파싱 캐시)
- **애플리케이션 로딩 시점에 쿼리 검증** ★ — 문법 오류를 실행 전에 잡음

```java
@Entity
@NamedQuery(name = "Member.findByUsername",
            query = "select m from Member m where m.username = :username")
public class Member { ... }

em.createNamedQuery("Member.findByUsername", Member.class)
  .setParameter("username", "회원1")
  .getResultList();
```

- XML(`META-INF/ormMember.xml`)이 **항상 우선권**, 운영 환경별로 다른 XML 배포 가능

> 참고: Spring Data JPA의 `@Query("select ...")`가 이름 없는 Named 쿼리로 등록돼 **로딩 시점 검증**을 그대로 누린다 → 실무에선 이걸 씀.

## 13. 벌크 연산

- "재고 10개 미만인 모든 상품 가격 10% 상승" → 변경 감지로 하면 조회 후 엔티티마다 UPDATE → **100건이면 UPDATE 100번**
- 벌크 연산: **쿼리 한 번으로 여러 row 변경**

```java
int resultCount = em.createQuery(
        "update Product p set p.price = p.price * 1.1 where p.stockAmount < :stockAmount")
        .setParameter("stockAmount", 10)
        .executeUpdate();   // 영향받은 엔티티 수 반환
```

- UPDATE, DELETE 지원 / INSERT(`insert into .. select`)는 하이버네이트 지원

### 주의 ★

- 벌크 연산은 **영속성 컨텍스트를 무시하고 DB에 직접 쿼리**
- 해결 2가지
  1. **벌크 연산을 먼저 실행** (영속성 컨텍스트에 아무것도 없을 때)
  2. **벌크 연산 수행 후 영속성 컨텍스트 초기화** (`em.clear()`) — 안 하면 1차 캐시의 옛날 값을 읽음
- 벌크 실행 전에 JPQL이라 **자동 flush**는 됨

> 참고: Spring Data JPA에선 `@Modifying(clearAutomatically = true)`로 2번을 자동 처리.

## 면접 포인트

- **페치 조인이란, 일반 조인과 차이?** 연관 엔티티/컬렉션을 SQL 한 번으로 함께 조회해 영속성 컨텍스트에 올리는 JPQL 기능. 일반 조인은 SELECT 절 엔티티만 채우고 연관은 LAZY 그대로.
- **컬렉션 페치 조인의 한계?** 페이징 불가(메모리 페이징), 둘 이상 컬렉션 불가, 별칭으로 필터링 금지. 페이징은 다대일 쪽에서 하거나 `@BatchSize`/`default_batch_fetch_size`로 N+1을 1+1로.
- **JPQL DISTINCT는 SQL DISTINCT와 뭐가 다른가?** SQL DISTINCT에 더해 애플리케이션에서 같은 식별자 엔티티를 제거. Hibernate 6부터는 자동.
- **벌크 연산 주의점?** 영속성 컨텍스트를 거치지 않아 1차 캐시와 DB가 불일치 → 먼저 실행하거나 실행 후 `em.clear()`.
- **묵시적 조인을 피하는 이유?** 항상 내부 조인이고 쿼리만 봐서는 조인이 보이지 않아 튜닝·디버깅이 어려움.
