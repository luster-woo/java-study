## 출력 예측

### 출력 1 · return과 finally

```java
static int test() {
    try {
        System.out.print("try ");
        return 1;
    } finally {
        System.out.print("finally ");
    }
}
System.out.println(test());
```

**답**

```
try finally 1
```

| 순서 | 일어나는 일 |
|---|---|
| 1 | `try ` 출력 |
| 2 | `return 1` → 반환값 1을 **저장만** 해 두고 아직 안 나감 |
| 3 | finally 실행 → `finally ` 출력 |
| 4 | 메서드 종료, 저장해 둔 1이 println으로 출력 |

- `print`라서 줄바꿈 없이 한 줄에 이어짐
- 관련 예제 : `src/day06/b_finally/FinallyTest.java` 2·3번 (finally에서 변수를 바꿔도 반환값은 그대로)

### 출력 2 · 다중 catch 흐름

```java
try {
    System.out.print("A ");
    Integer.parseInt("x");
    System.out.print("B ");
} catch (NumberFormatException e) {
    System.out.print("C ");
} catch (Exception e) {
    System.out.print("D ");
} finally {
    System.out.print("E ");
}
System.out.println("F");
```

**답**

```
A C E F
```

- `parseInt("x")`에서 NumberFormatException → try의 **나머지(B)는 건너뜀**
- catch는 위에서부터 검사해서 **처음 맞는 것 하나만** 실행 → C (D는 안 함, Exception도 맞긴 하지만 이미 처리됨)
- finally는 항상 → E
- 예외가 처리됐으니 try-catch 다음 줄도 정상 실행 → F

### 출력 3 · String 불변 vs StringBuilder

```java
String s = "abc";
s.concat("def");
s.toUpperCase();
StringBuilder sb = new StringBuilder("abc");
sb.append("def").reverse();
System.out.println(s + " " + sb + " " + sb.length());
```

**답**

```
abc fedcba 6
```

| 코드 | 결과 | 이유 |
|---|---|---|
| `s.concat("def")` | s는 그대로 `abc` | String은 **불변** → 새 문자열 `"abcdef"`를 만들어 리턴하지만 대입 안 해서 버려짐 |
| `s.toUpperCase()` | s는 그대로 `abc` | 마찬가지 (`s = s.toUpperCase()` 해야 바뀜) |
| `sb.append("def")` | `abcdef` | StringBuilder는 **자기 자신을 수정**하고 자기 자신을 리턴 |
| `.reverse()` | `fedcba` | 위 리턴값(같은 sb)에 이어서 호출 (메서드 체이닝) |
| `sb.length()` | `6` | |

### 출력 4 · record의 equals / toString

```java
record P(int x, int y) { }

P a = new P(1, 2);
P b = new P(1, 2);
System.out.println(a == b);
System.out.println(a.equals(b));
System.out.println(a);
```

**답**

```
false
true
P[x=1, y=2]
```

- `==` : **같은 객체인지**(주소) 비교 → new를 두 번 했으니 false. record라도 이건 안 바뀜
- `equals` : record가 **필드 값 기준**으로 자동 생성 → x, y가 같으니 true
- `toString` : 자동 생성 형식은 `이름[필드=값, 필드=값]`
- 관련 예제 : `src/day06/j_record/RecordTest.java` 2번

## 버그 찾기

### 버그 1 · 문제 세 개

```java
BufferedReader br = new BufferedReader(new FileReader("data.txt"));
try {
    String line = br.readLine();
    int n = Integer.parseInt(line);
} catch (Exception e) {
}
```

**답**

| # | 문제 | 왜 나쁜가 |
|---|---|---|
| 1 | **빈 catch** | 예외를 삼켜서 실패해도 아무도 모름 (APPENDIX "잡고 모르쇠") |
| 2 | **close 안 함** | 파일 자원이 반납되지 않음 |
| 3 | **너무 넓은 catch** | `Exception`으로 다 잡아서 파일 문제인지 숫자 문제인지 구분 불가 |

덤 : `new FileReader`가 try **밖**이라 파일이 없을 때 나는 FileNotFoundException(checked)은 여기서 안 잡힘 → 메서드에 `throws`가 없으면 컴파일 에러.

**고친 코드**

```java
try (BufferedReader br = new BufferedReader(new FileReader("data.txt"))) {   // 자동 close
    int n = Integer.parseInt(br.readLine());
} catch (IOException e) {                                // 파일 문제
    System.out.println("파일 읽기 실패: " + e.getMessage());
} catch (NumberFormatException e) {                      // 숫자 문제
    System.out.println("숫자가 아님");
}
```

### 버그 2 · catch 순서

```java
try {
    Files.readString(Path.of("a.txt"));
} catch (Exception e) {
    System.out.println("에러");
} catch (IOException e) {
    System.out.println("파일 에러");
}
```

**답** : 컴파일 에러

```
error: exception IOException has already been caught
```

- IOException은 Exception의 **자식** → 첫 번째 catch에서 이미 다 잡힘
- 두 번째 catch는 절대 실행될 수 없는 코드 → 컴파일러가 막음
- 고치기 : **자식(IOException)을 먼저, 부모(Exception)를 나중에**

```java
} catch (IOException e) {
    System.out.println("파일 에러");
} catch (Exception e) {
    System.out.println("에러");
}
```

## 빈칸 채우기

### 빈칸 1 · 파일 한 줄씩 읽기

```java
try (BufferedReader br = ____) {
    String line;
    while ((line = ____) != null) {
        System.out.println(line);
    }
}
```

**답** : `new BufferedReader(new FileReader("a.txt"))`, `br.readLine()`

- 보조 스트림(BufferedReader)은 혼자 못 씀 → 노드 스트림(FileReader)을 생성자에 넣어 연결 (스트림 체이닝)
- `readLine()`은 끝이면 **null** (read()의 -1이 아님!)
- catch가 없으니 이 코드가 든 메서드에 `throws IOException` 필요
- 관련 예제 : `src/day06/h_filter/BufferedTest.java` 2번

### 빈칸 2 · 사용자 정의 예외

```java
class InsufficientBalanceException extends ____ {
    InsufficientBalanceException(int shortage) {
        ____("잔액이 " + shortage + "원 부족합니다");
    }
}
```

**답** : `RuntimeException`, `super`

- `RuntimeException` 상속 → unchecked → 호출하는 쪽마다 throws를 안 달아도 됨
    - Spring의 `@Transactional`도 기본적으로 RuntimeException일 때 롤백
    - `Exception`을 써도 문법상 정답이지만, 그러면 checked라 처리 강제
- `super(메시지)` → 부모 생성자에 넘겨야 `getMessage()`로 꺼낼 수 있음
- 관련 예제 : `src/day06/d_custom/CustomExceptionTest.java`
