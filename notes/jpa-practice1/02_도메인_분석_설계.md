## 2. 도메인 모델과 테이블 설계

### 도메인 모델

```
Member 1 ─── N Order 1 ─── N OrderItem N ─── 1 Item ◁── Book / Album / Movie
                │                                  │
                1                                  N
                │                                  │
             Delivery                       N  Category (parent / child)
```

- 회원은 여러 번 주문 (1:N)
- 주문 : 상품 = N:M → **주문상품(OrderItem)** 엔티티로 1:N, N:1로 풀어냄 (보통 `OrderLine`, `LineItem`이라고도 부름)
- 상품은 공통 속성이 있어 **상속 구조**

### 엔티티 분석

| 엔티티 | 내용 |
|---|---|
| **Member** | 이름, 주소(`Address` 임베디드), 주문 리스트(`orders`) |
| **Order** | 주문 회원, 주문상품 리스트, 배송, 주문 날짜, 상태(`OrderStatus`: ORDER, CANCEL) |
| **OrderItem** | 주문한 상품, 주문 금액(`orderPrice`), 주문 수량(`count`) |
| **Item** | 이름, 가격, 재고수량(`stockQuantity`) — 주문하면 재고 감소. Book/Album/Movie |
| **Delivery** | 주문 시 하나 생성, 주문과 1:1. 주소, 상태(`DeliveryStatus`: READY, COMP) |
| **Category** | 상품과 N:M, `parent`·`child`로 계층 |
| **Address** | 값 타입(임베디드). Member와 Delivery에서 사용 |

> 참고: **회원이 주문 리스트를 갖는 건 실무에선 불필요**하다. 주문이 회원을 참조하는 것으로 충분(주문 조회는 회원 FK로 하면 됨). 여기선 1:N·N:1 양방향을 보여주려고 넣은 것.
> 참고: PDF 그림에서 Order–Delivery가 단방향으로 그려져 있는데 **양방향이 맞다**.

### 테이블

```
MEMBER   (member_id, name, city, street, zipcode)              ← Address가 그대로 컬럼으로
ORDERS   (order_id, member_id FK, delivery_id FK, order_date, status)
ORDER_ITEM (order_item_id, order_id FK, item_id FK, order_price, count)
ITEM     (item_id, dtype, name, price, stock_quantity, artist, etc, author, isbn, director, actor)  ← SINGLE_TABLE
DELIVERY (delivery_id, city, street, zipcode, status)
CATEGORY (category_id, parent_id FK, name)
CATEGORY_ITEM (category_id FK, item_id FK)                     ← @ManyToMany 중간 테이블
```

- `ORDER`가 아니라 **`ORDERS`**: `order by` 예약어 때문
- 테이블·컬럼명은 **소문자 + `_`** 스타일 사용 (회사마다 다르지만 일관성이 중요)

### 연관관계 매핑 분석

| 관계 | 종류 | 주인 (FK) |
|---|---|---|
| 회원 – 주문 | 1:N / N:1 **양방향** | `Order.member` → `ORDERS.MEMBER_ID` |
| 주문상품 – 주문 | N:1 **양방향** | `OrderItem.order` → `ORDER_ITEM.ORDER_ID` |
| 주문상품 – 상품 | N:1 **단방향** | `OrderItem.item` → `ORDER_ITEM.ITEM_ID` |
| 주문 – 배송 | 1:1 **양방향** | `Order.delivery` → `ORDERS.DELIVERY_ID` (주문을 더 자주 조회하므로 주문 쪽에 FK) |
| 카테고리 – 상품 | `@ManyToMany` | 예제용. **실무 사용 X** |

> **외래 키가 있는 곳을 연관관계의 주인으로.** 비즈니스상 우위로 정하면 안 된다. 자동차–바퀴면 FK가 있는 **바퀴**가 주인. 자동차를 주인으로 하면 관리하지 않는 바퀴 테이블의 FK가 업데이트돼 유지보수가 어렵고 추가 UPDATE 쿼리도 생긴다. ([기본편 5장](../jpa-basic/05_연관관계_매핑_기초.md))

## 3. 엔티티 클래스 개발 (강의 소스)

> 예제는 설명을 쉽게 하려고 **Getter·Setter를 다 열었다**. 실무에선 Getter는 열고 **Setter는 꼭 필요할 때만**.
> 이상적으로는 둘 다 없이 필요한 메서드만 제공하는 거지만, 데이터 조회가 너무 많아서 Getter는 다 여는 게 편하다. Getter는 호출해도 아무 일도 안 일어나지만 **Setter는 데이터를 바꾸므로** 막 열어두면 엔티티가 왜 바뀌는지 추적이 어려워진다 → 변경용 **비즈니스 메서드** 제공.

### Member

```java
@Entity @Getter @Setter
public class Member {
    @Id @GeneratedValue
    @Column(name = "member_id")
    private Long id;

    private String name;

    @Embedded
    private Address address;

    @OneToMany(mappedBy = "member")          // 읽기 전용 (주인은 Order.member)
    private List<Order> orders = new ArrayList<>();
}
```

> 엔티티 식별자는 `id`, PK 컬럼명은 `member_id`. 엔티티는 타입이 있어 `id`만으로 구분되지만 테이블은 타입이 없으니 관례상 `테이블명_id`. 중요한 건 **일관성**.

### Order

```java
@Entity
@Table(name = "orders")
@Getter @Setter
public class Order {
    @Id @GeneratedValue
    @Column(name = "order_id")
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "member_id")
    private Member member;                                   // 주인

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL)
    private List<OrderItem> orderItems = new ArrayList<>();

    @OneToOne(cascade = CascadeType.ALL, fetch = FetchType.LAZY)
    @JoinColumn(name = "delivery_id")
    private Delivery delivery;                               // 주인

    private LocalDateTime orderDate;                         // @Temporal 필요 없음

    @Enumerated(EnumType.STRING)
    private OrderStatus status;                              // ORDER, CANCEL

    //==연관관계 편의 메서드==// (양방향일 때 양쪽 세팅, 주로 컨트롤하는 쪽에 둠)
    public void setMember(Member member) {
        this.member = member;
        member.getOrders().add(this);
    }
    public void addOrderItem(OrderItem orderItem) {
        orderItems.add(orderItem);
        orderItem.setOrder(this);
    }
    public void setDelivery(Delivery delivery) {
        this.delivery = delivery;
        delivery.setOrder(this);
    }
}
```

- `cascade = ALL`: `persist(order)` 하나로 orderItems·delivery까지 저장 ([기본편 8장](../jpa-basic/08_프록시와_연관관계_관리.md))

### OrderItem

```java
@Entity @Table(name = "order_item") @Getter @Setter
public class OrderItem {
    @Id @GeneratedValue @Column(name = "order_item_id")
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "item_id")
    private Item item;          // 단방향

    @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "order_id")
    private Order order;        // 주인

    private int orderPrice;     // 주문 당시 가격 (상품 가격은 바뀔 수 있으니 따로 저장)
    private int count;
}
```

### Item (상속)

```java
@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)   // 한 테이블에
@DiscriminatorColumn(name = "dtype")
@Getter @Setter
public abstract class Item {
    @Id @GeneratedValue @Column(name = "item_id")
    private Long id;
    private String name;
    private int price;
    private int stockQuantity;

    @ManyToMany(mappedBy = "items")
    private List<Category> categories = new ArrayList<>();
}

@Entity @DiscriminatorValue("B") @Getter @Setter
public class Book extends Item { private String author; private String isbn; }
// Album("A"): artist, etc / Movie("M"): director, actor
```

### Delivery

```java
@Entity @Getter @Setter
public class Delivery {
    @Id @GeneratedValue @Column(name = "delivery_id")
    private Long id;

    @OneToOne(mappedBy = "delivery", fetch = FetchType.LAZY)
    private Order order;

    @Embedded
    private Address address;

    @Enumerated(EnumType.STRING)                     // ORDINAL 쓰면 중간에 값 추가 시 장애
    private DeliveryStatus status;                   // READY, COMP
}
```

### Category (N:M + 자기 참조)

```java
@Entity @Getter @Setter
public class Category {
    @Id @GeneratedValue @Column(name = "category_id")
    private Long id;
    private String name;

    @ManyToMany
    @JoinTable(name = "category_item",
            joinColumns = @JoinColumn(name = "category_id"),
            inverseJoinColumns = @JoinColumn(name = "item_id"))
    private List<Item> items = new ArrayList<>();

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "parent_id")
    private Category parent;

    @OneToMany(mappedBy = "parent")
    private List<Category> child = new ArrayList<>();

    public void addChildCategory(Category child) {
        this.child.add(child);
        child.setParent(this);
    }
}
```

> `@ManyToMany`는 중간 테이블(CATEGORY_ITEM)에 컬럼 추가가 안 되고 세밀한 쿼리가 어렵다 → 실무에선 `CategoryItem` 엔티티를 만들어 `@ManyToOne`, `@OneToMany`로 풀자.

### Address (값 타입)

```java
@Embeddable
@Getter                                  // Setter 없음 → 불변
public class Address {
    private String city;
    private String street;
    private String zipcode;

    protected Address() {}               // JPA 스펙상 기본 생성자 필요 (public보다 protected가 안전)

    public Address(String city, String street, String zipcode) { ... }
}
```

- 값 타입은 **변경 불가능하게** 설계: `@Setter` 제거, 생성자에서 모두 초기화
- JPA가 기본 생성자를 요구하는 이유: 구현 라이브러리가 **리플렉션·프록시**로 객체를 만들 수 있어야 하므로

## 4. 엔티티 설계 시 주의점 ★

### ① 엔티티에는 가급적 Setter를 사용하지 말자

- Setter가 다 열려 있으면 변경 포인트가 너무 많아 유지보수가 어렵다 → 나중에 리팩토링으로 제거

### ② 모든 연관관계는 지연로딩으로 설정!

- 즉시로딩(EAGER)은 예측이 어렵고 어떤 SQL이 실행될지 추적하기 어렵다. **특히 JPQL 실행 시 N+1**
- 실무에서 **모든 연관관계는 LAZY**
- 함께 조회해야 하면 **fetch join** 또는 **엔티티 그래프**
- **`@XToOne`(`@OneToOne`, `@ManyToOne`)은 기본이 EAGER → 직접 LAZY로** (`@XToMany`는 기본 LAZY)

### ③ 컬렉션은 필드에서 초기화하자

- `null` 문제에서 안전
- 하이버네이트는 영속화할 때 컬렉션을 **내장 컬렉션(PersistentBag)으로 감싸서 바꾼다** → 임의의 메서드에서 컬렉션을 새로 만들어 덮어쓰면 내부 메커니즘이 깨질 수 있음

```java
Member member = new Member();
System.out.println(member.getOrders().getClass());  // class java.util.ArrayList
em.persist(member);
System.out.println(member.getOrders().getClass());  // class org.hibernate.collection...PersistentBag
```

- → **필드 레벨에서 생성하고, 이후엔 바꾸지 말 것**

### ④ 테이블·컬럼명 생성 전략

- 하이버네이트 기본: 필드명을 그대로 컬럼명으로
- **스프링 부트 기본 설정**: 엔티티(필드) → 테이블(컬럼)
  1. 카멜 케이스 → 언더스코어 (`memberPoint` → `member_point`)
  2. `.`(점) → `_`
  3. 대문자 → 소문자
- 적용 2단계
  1. **논리명**: 컬럼·테이블명을 명시하지 않으면 `spring.jpa.hibernate.naming.implicit-strategy` 적용
  2. **물리명**: 모든 논리명에 `spring.jpa.hibernate.naming.physical-strategy` 적용 → 회사 룰(`username` → `usernm`)로 바꿀 수도 있음

> 참고: PDF에 적힌 `SpringPhysicalNamingStrategy`는 Boot 2 기준. **Boot 3에서는 하이버네이트의 `CamelCaseToUnderscoresNamingStrategy`가 기본 물리 전략**이다 (동작은 같음).

### (영상에서 다루는) cascade와 연관관계 편의 메서드

- `Order`의 `orderItems`, `delivery`에 `cascade = ALL` → 주문 하나만 persist
- 편의 메서드는 양쪽 중 **핵심적으로 컨트롤하는 쪽**에 둔다 (`Order.setMember`, `Order.addOrderItem`, `Category.addChildCategory`)
