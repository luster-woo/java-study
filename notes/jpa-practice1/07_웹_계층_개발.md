## 한 줄 요약

화면은 **폼 객체**로 받고, 엔티티 수정은 **merge가 아니라 변경 감지**로 — 서비스에 id와 바꿀 값만 넘겨서 트랜잭션 안에서 영속 엔티티를 바꾼다.

## 2. 회원 등록 — 폼 객체 + 검증

```java
@Getter @Setter
public class MemberForm {
    @NotEmpty(message = "회원 이름은 필수 입니다")   // jakarta.validation
    private String name;
    private String city;
    private String street;
    private String zipcode;
}
```

```java
@Controller
@RequiredArgsConstructor
public class MemberController {
    private final MemberService memberService;

    @GetMapping("/members/new")
    public String createForm(Model model) {
        model.addAttribute("memberForm", new MemberForm());   // 빈 폼 객체 (검증 화면에서 필드 접근용)
        return "members/createMemberForm";
    }

    @PostMapping("/members/new")
    public String create(@Valid MemberForm form, BindingResult result) {
        if (result.hasErrors()) {                             // 오류를 담고 다시 폼으로
            return "members/createMemberForm";
        }
        Address address = new Address(form.getCity(), form.getStreet(), form.getZipcode());
        Member member = new Member();
        member.setName(form.getName());
        member.setAddress(address);
        memberService.join(member);
        return "redirect:/";                                  // PRG: 새로고침 재전송 방지
    }
}
```

- `@Valid`: 폼의 `@NotEmpty` 검증 실행
- **`BindingResult`**: `@Valid` 바로 뒤에 두면 오류가 나도 컨트롤러가 실행되고 오류가 여기 담김 (없으면 400 에러 페이지)
- 화면: `th:object="${memberForm}"`, `th:field="*{name}"`(id·name·value 자동), `${#fields.hasErrors('name')}`로 빨간 테두리, `th:errors="*{name}"`로 메시지 출력 → 입력값도 유지됨

### 폼 객체 vs 엔티티 직접 사용 ★

- 요구사항이 정말 단순하면 엔티티를 등록·수정 화면에 바로 써도 된다
- 하지만 화면 요구사항이 복잡해지면 엔티티에 화면용 기능이 늘어 **엔티티가 화면에 종속**되고 지저분해져 유지보수가 어려워진다
- **실무에서 엔티티는 핵심 비즈니스 로직만**, 화면·API에 맞는 건 **폼 객체나 DTO**로. 엔티티는 최대한 순수하게
- 특히 **API를 만들 때는 절대 엔티티를 외부로 반환하지 말 것** (필드 추가로 API 스펙이 바뀌고, 비밀번호 같은 정보 노출) — 활용2에서 자세히

### 처음 버전 (소스에선 주석 처리됨) — 준영속 엔티티 + merge

```java
@PostMapping("/items/{itemId}/edit")
public String updateItem(@ModelAttribute("form") BookForm form) {
    Book book = new Book();
    book.setId(form.getId());          // ← 이미 DB에 있는 id를 가진 객체를 new로 만듦 = 준영속
    book.setName(form.getName());
    // ...
    itemService.saveItem(book);        // ItemRepository.save → id가 있으니 em.merge(book)
    return "redirect:/items";
}
```

- 파라미터로 넘어와 직접 만든 `book`은 **준영속 상태** → 영속성 컨텍스트 지원을 못 받아 값을 바꿔도 **변경 감지 X**

> ⚠️ 보안: `id`를 조작해서 남의 상품을 수정할 수 있으니, 실무에선 서비스/컨트롤러에서 **이 사용자에게 수정 권한이 있는지** 반드시 검증해야 한다 (강의 영상 언급).

## 6. 변경 감지와 병합(merge) — 정말 중요 ★★★

### 준영속 엔티티?

- **영속성 컨텍스트가 더는 관리하지 않는 엔티티**
- `itemService.saveItem(book)`의 `book`처럼, 이미 DB에 저장돼 **식별자가 있는** 객체는 임의로 `new`로 만들었어도 준영속으로 볼 수 있다

### 준영속 엔티티를 수정하는 2가지 방법

**① 변경 감지 (dirty checking)**

```java
@Transactional
void update(Item itemParam) {                                  // itemParam: 준영속
    Item findItem = em.find(Item.class, itemParam.getId());   // 같은 엔티티를 영속 상태로 조회
    findItem.setPrice(itemParam.getPrice());                  // 데이터 수정
}   // 커밋 시점에 변경 감지 → UPDATE
```

- 트랜잭션 안에서 엔티티를 다시 조회하고, **변경할 값만 골라서** 수정

**② 병합 (merge)** — 준영속 엔티티를 영속 상태로 바꿀 때 쓰는 기능

```java
@Transactional
void update(Item itemParam) {
    Item mergeItem = em.merge(itemParam);    // 반환값이 영속 엔티티. itemParam은 여전히 준영속!
}
```

병합 동작 방식
1. `merge()` 실행
2. 준영속 엔티티의 식별자로 **1차 캐시에서 조회** (없으면 DB에서 조회해 1차 캐시에 저장)
3. 조회한 **영속 엔티티에 준영속 엔티티의 값을 전부 채워 넣음** (모든 필드 교체)
4. 영속 엔티티(`mergeItem`) 반환 → 커밋 시 변경 감지로 UPDATE

> 즉 merge = "①을 JPA가 대신 해주는데, **모든 필드를 덮어쓴다**"

### 주의 — merge의 위험

- 변경 감지는 원하는 속성만 바꾸지만, **병합은 모든 속성이 변경**된다
- **값이 없으면 null로 업데이트**될 위험 (예: 수정 폼에 가격 필드가 없으면 가격이 null/0이 됨)
- 실무에선 수정 가능한 데이터만 화면에 노출하므로, merge를 쓰려면 폼에서 모든 데이터를 항상 유지해야 해서 오히려 번거롭다

### ItemRepository.save() 다시 보기

```java
public void save(Item item) {
    if (item.getId() == null) em.persist(item);   // 신규
    else                      em.merge(item);     // 준영속 → 병합
}
```

- 저장과 수정(병합)을 하나로 처리 → 클라이언트가 구분할 필요 없음 (스프링 데이터 JPA의 `save()`도 같은 방식)
- 영속 상태 엔티티는 변경 감지로 자동 수정되니 **별도의 수정 메서드가 필요 없고, 없다**
- `@GeneratedValue`일 때만 정상 동작 (직접 할당 id면 id 없이 `persist` → 예외)

### 가장 좋은 해결 방법 ★

> **엔티티를 변경할 때는 항상 변경 감지를 사용하세요**

- **컨트롤러에서 어설프게 엔티티를 생성하지 마세요**
- 트랜잭션이 있는 **서비스 계층에 식별자(id)와 변경할 데이터를 명확하게 전달** (파라미터 or DTO)
- 서비스 계층에서 **영속 상태의 엔티티를 조회하고 직접 변경**
- 트랜잭션 커밋 시점에 변경 감지 실행

```java
/** 상품 수정, 권장 코드 — 소스에서 실제 사용 */
@PostMapping("/items/{itemId}/edit")
public String updateItem(@PathVariable Long itemId, @ModelAttribute("form") BookForm form) {
    itemService.updateItem(itemId, form.getName(), form.getPrice(), form.getStockQuantity());
    return "redirect:/items";
}
```

```java
@Transactional
public void updateItem(Long id, String name, int price, int stockQuantity) {
    Item item = itemRepository.findOne(id);   // 영속 상태
    item.setName(name);                        // → 더 좋게: item.change(name, price, stockQuantity)
    item.setPrice(price);
    item.setStockQuantity(stockQuantity);
}
```

## 면접 포인트

- **준영속 엔티티를 수정하는 방법 2가지와 차이?** 변경 감지(영속 엔티티를 다시 조회해 원하는 필드만 변경)와 병합(merge, 준영속 값으로 영속 엔티티의 모든 필드를 교체). 병합은 누락 필드가 null로 덮일 위험 → 변경 감지 권장.
- **`em.merge(item)` 후 `item`은 영속 상태인가?** 아니다. 반환된 객체가 영속이고 파라미터는 여전히 준영속.
- **폼 객체/DTO를 쓰는 이유?** 엔티티가 화면·API 스펙에 종속되지 않게 하고, 검증 어노테이션 같은 화면 관심사를 엔티티에서 분리.
- **컨트롤러에서 엔티티 대신 식별자를 서비스로 넘기는 이유?** 트랜잭션 안에서 조회해야 영속 상태라 변경 감지·지연 로딩이 정상 동작.
