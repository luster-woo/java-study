## 1. Framework

### Framework란?

- 사전적 정의: **틀(Frame)** 을 가지고 하는 작업(work), 또는 틀 자체
- 일상의 예: 사진(content)만 빠지고 뼈대는 갖춰진 **반제품 액자**
  - 액자에 사진을 끼우면 바로 걸 수 있음 → "Frame + content"
- SW에서: **비즈니스 로직만 빠진, 뼈대가 갖춰진 반제품 애플리케이션**
  - 예: 발표 자료를 만들 때 PowerPoint를 쓰면 애니메이션·도형 같은 기능은 이미 있음 → 나는 발표 내용만 채우면 됨

| 비유 | Frame | Content |
|---|---|---|
| 액자 | 액자 틀 | 사진 |
| 발표 | PowerPoint | 발표 내용 |
| 애플리케이션 | Framework | 비즈니스 로직 |

### Spring Framework

- **자바 애플리케이션 개발을 위한 경량 framework**
- 역할 분담
  - 프레임워크: 비즈니스 로직과 무관하면서 귀찮고 어렵고 **모듈화할 수 있는 일**을 담당
  - 개발자: 프레임워크에 맞는 **비즈니스 로직을 공급**하는 데 집중
- JDBC 작업에서 개발자 역할의 변화

| 작업 | 스프링을 몰랐을 때 (개발자가 직접) | 스프링을 알게 된 후 |
|---|---|---|
| DB 관리 | 직접 | 스프링이 처리 (설정은 필요) |
| Tx 처리 | 직접 코드 작성 | **선언적 Tx 처리** |
| JDBC 코드 | 직접 사용 | **템플릿 제공** |
| 예외 관리 | 직접 | **범용 예외 처리** |
| 비즈니스 로직 | 개발자 | 개발자 → 여기에만 집중 |

- 스프링은 개발자를 도와주기 위한 **도구** — 많은 기술이 모인 자바의 종합 예술
  - 프로젝트 목록: https://spring.io/projects
- 쉽지 않음 → 처음엔 **원리보다 사용법 위주**로 접근, 하다 보면 원리가 따라옴
  - PowerPoint 원리를 몰라도 PowerPoint는 쓸 수 있는 것과 같음

### Spring Boot

- 또 다른 스프링이 아니라 **스프링 애플리케이션을 개발하는 일종의 템플릿**
- **설정 자동화** → 스프링 개발 속도 향상
- **단위 테스트 강화** → 프로젝트 안정성 강화
- 결과적으로 개발자는 비즈니스 로직에 더 집중

| Boot가 해 주는 것 | 예 |
|---|---|
| 의존성 버전 관리 | 라이브러리 버전 조합을 맞춰 줌 |
| 설정 자동화 | DB 쓰려면 DataSource 연결, 웹 서비스하려면 WAS 설정 → 자동 |
| 프로덕션 레디 | 운영 환경에 필요한 기능 |
| 단위 테스트 강화 | 테스트 지원 |

- 주의: **Boot 바보가 되지 말 것** — 자동 설정을 커스터마이징할 수 있어야 함

### 주요 특징 — POJO 기반의 DI, AOP, PSA

```
        DI
      /    \
   AOP──POJO──PSA
```

- 세 기술(DI, AOP, PSA)이 가운데의 **POJO**를 감싸고 동작하는 구조

#### DI (Dependency Injection, 의존성 주입)

- 생각해 볼 질문: 수업을 듣기 위해 무엇에 의존하는가? 일반 객체에서 의존성이란? 의존성을 없앨 수 있을까? 어떻게 관리되는가?
- 의존성을 **주입받아** 사용 → 의존성이 바뀌어도 **의존하는 객체는 변경할 필요가 없음**
- 코드의 **유지보수성 향상**
- 자세한 내용은 [의존성과 DI](04_의존성과_DI.md)

#### AOP (Aspect Oriented Programming, 관점 지향 프로그래밍)

- 비유: 요리사가 요리도 하고 정산도 하면 바쁨 → 캐셔를 고용하면 요리사는 요리에만 집중
  - 정산은 캐셔의 **관점**에서 따로 처리
- 비즈니스 로직에서 부가적인 **횡단 관심사** 코드를 분리·모듈화하고, 필요한 곳에 적용
- 개발자는 **핵심 관심사**에 집중

#### PSA (Portable Service Abstraction)

- 서비스를 **추상화**해서 자유롭게 바꿔 끼울 수 있게 함
  - 추상화: 복잡한 구현을 숨기고 단순하게 접근하게 하는 것
- 어렵고 복잡한 개념을 **특정 환경에 종속되지 않고** 쉽게 쓰도록 추상화된 레이어(interface 및 구현체) 제공
- 예: 트랜잭션 처리

```java
// 추상화 전: 기술마다 공부해서 따로 처리
void TX_처리_필요(MyBatis, 100) { /* MyBatis 공부 후 처리 */ }
void TX_처리_필요(JPA, 100)     { /* JPA 공부 후 처리 */ }

// 추상화 후: interface TXManager 하나로 처리
//   TX_for_MyBatis → DataSourceTransactionManager
//   TX_for_JPA     → JpaTransactionManager
@Transactional   // 설정 기반으로 구현체 선택
void TX_처리_필요(TXManager, 100) { ... }
```

- JPA를 쓰든 MyBatis를 쓰든 **스프링에서 Tx 처리하는 방법은 동일**

#### POJO (Plain Old Java Object)

- 비즈니스 로직 구현은 지금까지 하던 대로 **평범한 객체**를 만들면 됨 — DI, AOP, PSA라는 "마법"은 스프링 프레임워크가 담당
- **특정 인터페이스 구현·상속 등이 필요 없는** 일반 자바 클래스

| 장점 | 내용 |
|---|---|
| 자유롭고 유연함 | 특정 프레임워크·라이브러리에 종속되지 않음 |
| 유지보수 용이 | 코드가 단순·평범해서 이해와 수정이 쉬움 |
| 높은 생산성 | 복잡한 규칙 신경 쓰지 않고 핵심 기능만 구현 → 개발 속도 향상 |
| 테스트 용이 | 특별한 환경 없이 순수 자바 코드만으로 기능 테스트 가능 |

### 그래서 탄생한 Spring Framework

- POJO 기반의 DI·AOP·PSA 위에 여러 프로젝트가 더해져 **못 하는 게 없는 만능**이 됨 → https://spring.io/projects
