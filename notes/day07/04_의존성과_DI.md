## 1. 의존성과 DI

### 우리의 생활과 DI — 의존성

- **의존성**: 어떤 행동을 하기 위해 의존하는 도구
- 상황: 손빨래가 금지되어 모든 사람은 반드시 세탁기를 가져야 함
  - 나는 세탁기에 **의존**함 → 세탁기는 나의 **의존성**
  - 사람 객체와 세탁기 객체의 관계 = **has-a**
- 의존성을 없앨 수 있을까? → 없앨 수는 없고, **어떻게 보유하느냐**가 문제

### 의존성을 보유하는 방법 — 구매 vs 렌탈

| 비교 | 구매 (의존성 생성) | 렌탈 (의존성 주입) |
|---|---|---|
| 핵심 기능 | 빨래 | 빨래 |
| 초기 비용 | 모든 상품을 직접 선정·비교 → 많은 리소스 | 1차 비교·선정은 렌탈 업체가 → 적은 리소스 |
| 보유 과정 | 내 것이니 마음대로 (중고 판매, 튜닝, 꾸미기) | 내 것 같지만 아님 (팔면 계약 위반, 반납 시 원상 복구) |
| 관리 | 고장 수리·청소 등 직접 관리 | 렌탈 업체가 관리 → 유지보수 용이 |

- 빨래하려고 보유한 세탁기는 팔 일은 없지만 관리는 언제나 필요 → 렌탈이 귀찮은 일을 대신해 줌
- 대신 세탁기가 "내 것"이 아님 → **제어 주체가 바뀜**
- 이제 의존성을 구입하는 시대가 아니라 **주입받아 쓰는 시대**

### 스프링의 빈과 의존성 관리

- **빈(Bean)**: 스프링 프레임워크가 **생성하고 관리하는 자바 객체** (나, 렌탈 업체, 세탁기, ...)
  - 스프링은 빈의 생성, 의존 관계 설정, 객체 관리 등 **빈의 라이프 사이클**을 관리
  - 그래서 스프링을 **빈의 컨테이너**라고 함 (Servlet Container와 같은 맥락)
- **의존 관계**: 어떤 객체(빈)가 비즈니스 로직 처리를 위해 다른 객체(빈)에 의존하는 관계 — 객체 간 has-a 관계
- 의존 관계를 관리하려고 **DI** 개념을 사용하며, 이 과정에서 **제어의 역전**이 발생
  - 스프링을 **IoC(Inversion of Control) 컨테이너**라고도 부름
  - Framework에서는 거의 대부분 제어의 역전이 발생함

### DI의 필요성 1 — 직접 생성

```java
public class WasherUser {
    SWasher washer;                  // has-a 관계 - 의존성

    public WasherUser() {
        this.washer = new SWasher(); // 의존성을 직접 생성
    }

    public void useWasher(String clothes) {  // 비즈니스 로직
        washer.wash(clothes);
    }
}

public class SWasher {
    public void wash(String clothes) {
        System.out.println("SWasher로 세탁: " + clothes);
    }
}
```

- SWasher가 질려서 다른 세탁기로 바꾸려면? → 필드 타입, 생성 코드를 모두 고쳐야 함
- **유지보수성이 좋지 않음**

### DI의 필요성 2 — 인터페이스 이용

```java
public class WasherUser {
    Washer washer;                   // 인터페이스 타입으로 선언

    public WasherUser() {
        this.washer = new SWasher(); // 여전히 직접 생성
    }

    public void useWasher(String clothes) {
        washer.wash(clothes);
    }
}
```

- 필드 타입이 인터페이스라 **변경 포인트가 줄어듦**
- 그래도 `new SWasher()`를 직접 하는 한 세탁기를 바꿀 때마다 WasherUser를 수정해야 함 → 여전히 야근

### DI의 필요성 3 — Factory Pattern + 주입

- WasherUser는 더 이상 세탁기를 **생성하지 않음** → 외부에서 **주입**받음
- 세탁기는 **WasherFactory**를 통해 얻어서 주입

```java
public class WasherUser {
    Washer washer;   // has-a 관계 - 의존성

    // 의존성을 직접 생성하지 않고 외부에서 주입받음
    public WasherUser(Washer washer) {
        this.washer = washer;
    }
    // ...
}

public class WasherFactory {
    public static Washer createWasher(String type) {
        return switch (type) {        // switch 식 (Java 14+)
            case "L" -> new LWasher();
            default  -> new SWasher();
        };
    }
}
```

- 새로운 걸 쓰고 싶으면 바꿔 달라고 하면 됨
- 하지만 남은 문제
  - 팩토리 작성·관리가 복잡하고 귀찮음 → 누가 대신 해 줬으면
  - 호출할 때마다 **새 세탁기**가 만들어짐 → 하나만 있으면 되는데? (Singleton 필요)

- 순수 자바로 1단계(직접 생성)와 3단계(팩토리 + 주입)를 비교한 코드

```java
public class WasherTest {
    public static void main(String[] args) {
        WasherUser1 u1 = new WasherUser1();        // 1단계: 내부에서 직접 new
        u1.useWasher("셔츠");

        WasherUser3 u3 = new WasherUser3(WasherFactory.createWasher("L")); // 생성자 주입
        u3.useWasher("이불");

        u3.setWasher(WasherFactory.createWasher("S"));                     // setter 주입으로 교체
        u3.useWasher("양말");
    }
}

interface Washer { void wash(String clothes); }

class SWasher implements Washer {
    public void wash(String clothes) { System.out.println("SWasher로 세탁: " + clothes); }
}

class LWasher implements Washer {
    public void wash(String clothes) { System.out.println("LWasher로 세탁: " + clothes); }
}

class WasherUser1 {
    SWasher washer;
    WasherUser1() { this.washer = new SWasher(); }
    void useWasher(String clothes) { washer.wash(clothes); }
}

class WasherFactory {
    static Washer createWasher(String type) {
        return switch (type) {
            case "L" -> new LWasher();
            default  -> new SWasher();
        };
    }
}

class WasherUser3 {
    Washer washer;
    WasherUser3(Washer washer) { this.washer = washer; }
    void setWasher(Washer washer) { this.washer = washer; }
    void useWasher(String clothes) { washer.wash(clothes); }
}
/* 결과
SWasher로 세탁: 셔츠
LWasher로 세탁: 이불
SWasher로 세탁: 양말
*/
```

- WasherUser3는 어떤 세탁기인지 몰라도 동작함 → 바꾸는 쪽(외부)만 수정하면 됨

### 최종 — Spring Framework의 등장

- Spring은 WasherUser, SWasher, LWasher 같은 객체를 **빈**으로 관리 → Spring은 **빈의 Container**
  - 빈을 특별하게 만들 필요 없이 그냥 **POJO**로 만들면 됨
- Spring은 설정에 따라 WasherUser의 의존성(Washer)에 자기가 가진 빈을 **주입** → **DI**
  - Factory 같은 것은 필요 없음, 빈은 **Singleton**으로 관리

```java
public class WasherUser {
    Washer washer;   // has-a 관계 - 의존성

    public WasherUser(Washer washer) {   // Spring이 SWasher 또는 LWasher 빈을 주입
        this.washer = washer;
    }
}
```

- 프레임워크 사용 전: 빈 관리를 **개발자가 직접** 컨트롤
- 프레임워크 사용 후: **프레임워크가 처리** → 개발자는 프레임워크가 원하는 대로 만들어 주기만 하면 됨
  - **제어의 역전(IoC)** 발생 → IoC Container

### 결국 DI란

- 객체의 의존성, 즉 **멤버 변수를 외부에서 주입**하는 것
- 멤버 변수를 설정하는 방법 = **DI 방법**

| 방법 | 코드 |
|---|---|
| field에 직접 할당 | `user.washer = washer;` |
| 생성자 활용 | `public WasherUser(Washer washer) { this.washer = washer; }` |
| setter 메서드 활용 | `public void setWasher(Washer washer) { this.washer = washer; }` |

### Spring의 빈 관리 과정

```
 1. POJO로 빈 구성              2. 빈 구성 정보(메타 정보) 전달
 WasherUser, Washer,  ───────►  ┌──────── 스프링 컨테이너 ────────┐
 SWasher, LWasher               │ 3. 빈 생성 및 주입               │
                                │    SWasher (생성)               │
                                │    LWasher (생성)               │
                                │    WasherUser (생성) ◄─ 주입     │
                                └─────────────────────────────────┘
                                     ▲ 4. 빈 요청      │ 5. 빈 반환
                                     │                 ▼
                                   WasherUserTest — 6. 빈 사용
```

1. 개발자는 **POJO**로 빈을 작성
2. **메타 정보**(빈의 생성 방법, 관계 설정 정보)를 스프링 컨테이너에 전달
3. 런타임에
   - 스프링은 메타 정보를 보고 빈 객체를 생성 → **싱글턴** 형태로 관리
   - 빈 관계 정보에 따라 빈 **주입** 처리
4. ~ 6. 사용하는 쪽은 컨테이너에 빈을 요청해서 받아 사용

> 참고: 교재의 `return switch (type) { case "L" -> ... }`는 switch 식으로 Java 14부터 표준. Spring 6은 Java 17 이상이 필요하므로 그대로 사용 가능.
