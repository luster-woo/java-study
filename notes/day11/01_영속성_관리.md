## 영속성 컨텍스트

### 정의
- **영속성 컨텍스트(persistence context)**: 엔티티 인스턴스들의 집합으로, 어떤 영속 식별자(기본 키)에 대해서도 **인스턴스가 딱 하나**만 있는 곳 (JPA 명세의 정의)
- 이 안에서 엔티티 인스턴스와 그 생명주기가 **관리(managed)** 됨
- `EntityManager` 하나는 영속성 컨텍스트 하나와 연결됨 → `EntityManager` API는 결국 **영속성 컨텍스트를 다루는 메서드 모음**
- Hibernate의 `Session`도 같은 개념: "논리적 트랜잭션에 묶인 관리 엔티티 집합"
- 눈에 보이는 객체가 아니라 논리적 개념 → `em.persist(member)`는 "DB에 저장"보다 정확히는 "**영속성 컨텍스트에 넣어 관리 상태로 만든다**"

```
EntityManager ─── 영속성 컨텍스트
                    ┌───────────────────────────────┐
                    │  @Id(키)      엔티티(값)       │
                    │  1L      →   Member(1, "A")   │  ← 같은 키엔 인스턴스 1개
                    │  2L      →   Member(2, "B")   │
                    └───────────────────────────────┘
                              │ flush (커밋 때 등)
                              ▼
                             DB
```

### EntityManager가 컨텍스트를 얻는 두 방식

| 방식 | 얻는 법 | 영속성 컨텍스트 |
|---|---|---|
| **컨테이너 관리** | `@PersistenceContext EntityManager em;` 주입 | 현재 트랜잭션을 따라 **자동 전파** → 같은 트랜잭션 안의 컴포넌트들이 같은 컨텍스트 공유 |
| **애플리케이션 관리** | `emf.createEntityManager()` | `EntityManager`마다 **새로운 독립 컨텍스트**. 생성·종료를 코드가 직접 |

- `EntityManager`는 스레드 안전하지 않고 `EntityManagerFactory`는 스레드 안전함

## 엔티티 생명주기

### 네 가지 상태

| 상태 | JPA 용어 | Hibernate 용어 | 영속 식별자 | 영속성 컨텍스트와 |
|---|---|---|---|---|
| **비영속** | new | transient | 없음 | 관계 없음 (그냥 `new` 한 객체) |
| **영속** | managed | persistent | 있음 | **관리됨** |
| **준영속** | detached | detached | 있음 | 한때 관리됐지만 지금은 분리됨 |
| **삭제** | removed | (삭제 예정 표시) | 있음 | 관리되지만 DB에서 **삭제 예정** |

### 상태 전이

```
          new Member()
               │
          [비영속]
               │ persist()
               ▼
 find()/JPQL ─▶ [영속] ──── remove() ───▶ [삭제] ── flush/커밋 ──▶ DB에서 DELETE
 조회 결과        ▲  │                       │
                 │  │ detach() / clear()      │ persist() 다시 하면 영속으로
         merge() │  │ / close()               └──────────────▶ [영속]
                 │  ▼
              [준영속]
```

- `find()`나 쿼리로 받은 인스턴스는 처음부터 **영속** 상태
- `merge()`: 준영속(또는 비영속) 객체의 **상태를 복사해** 영속 인스턴스에 반영하고, 그 **영속 인스턴스를 반환** → 넘긴 객체 자체가 영속이 되는 게 아님

```java
Member detached = ...;              // 준영속
Member managed = em.merge(detached); // managed가 영속, detached는 여전히 준영속
```

### 연산별 규칙 (상태에 따라 다르게 동작)

| 호출 | 비영속(new) | 영속(managed) | 준영속(detached) | 삭제(removed) |
|---|---|---|---|---|
| `persist` | 영속이 됨 | 무시(cascade는 전파) | `IllegalArgumentException` 또는 커밋 실패 | 다시 영속이 됨 |
| `remove` | 무시(cascade는 전파) | 삭제 상태가 됨 | `IllegalArgumentException` 또는 커밋 실패 | 무시 |

## 영속성 컨텍스트의 이점

### 1차 캐시 — 조회 시 컨텍스트 먼저
- `em.find(엔티티, 기본키)`는 **영속성 컨텍스트에 이미 그 엔티티가 있으면 거기서 반환**함 (JPA 명세의 `find` 설명) → DB를 다시 조회하지 않음
- 이렇게 컨텍스트 내부가 엔티티를 보관하는 역할을 흔히 **1차 캐시**라고 부름 (Hibernate의 2차 캐시와 구분)
- 컨텍스트는 트랜잭션(요청) 단위로 짧게 살기 때문에, 애플리케이션 전체가 공유하는 캐시는 아님

```java
// DB에 id=1 회원이 이미 있다고 가정
Member a = em.find(Member.class, 1L);       // 컨텍스트에 없음 → SELECT, 결과를 컨텍스트에 보관
Member b = em.find(Member.class, 1L);       // 컨텍스트에서 반환 → SELECT 없음

em.clear();                                 // 컨텍스트 비움 (a, b는 준영속)
Member c = em.find(Member.class, 1L);       // 다시 컨텍스트에 없음 → SELECT
```

```java
Member member = new Member(2L, "회원2");
em.persist(member);                         // 컨텍스트에 보관
Member d = em.find(Member.class, 2L);       // 컨텍스트에서 반환 → SELECT 없음 (d == member)
```

### 동일성 보장
- 한 컨텍스트 안에서 같은 기본 키에 대한 인스턴스는 하나뿐 → 같은 id를 두 번 조회해도 **같은 객체**

```java
Member a = em.find(Member.class, 1L);
Member b = em.find(Member.class, 1L);
System.out.println(a == b);   // true (같은 영속성 컨텍스트 안)
```

- `==` 비교가 의미 있게 됨 → SQL을 직접 실행해 매번 새 객체를 만드는 방식과의 차이 ([JPA 소개](../day10/07_JPA_소개.md)의 IdentityTest)

### 쓰기 지연
- `persist()`를 불러도 INSERT가 그 자리에서 실행되지 않을 수 있음 → Hibernate 문서: `Session` 메서드가 SQL을 **동기적으로 실행하지 않는 경우가 많음**
- 변경 내용은 컨텍스트에 쌓였다가 **flush 시점**(대표적으로 트랜잭션 커밋)에 INSERT·UPDATE·DELETE로 DB에 반영됨
- JPA 명세상 `persist` 대상 엔티티가 이미 DB에 있으면 `EntityExistsException`이 persist 호출 때 날 수도, **flush·커밋 때** 날 수도 있음 → SQL이 나중에 나갈 수 있다는 뜻

```java
tx.begin();
em.persist(new Member(10L, "A"));   // 기본 키를 직접 지정한 엔티티
em.persist(new Member(11L, "B"));
// 여기까지는 컨텍스트에만 있음
tx.commit();                        // flush → INSERT 2건 실행 후 커밋
```

### 변경 감지 (dirty checking)
- 영속 상태 엔티티의 값이 바뀌면 컨텍스트가 **자동으로 감지**해서 flush 때 UPDATE를 실행함 → Hibernate 문서가 이 과정을 **dirty checking**이라 부름
- 그래서 `EntityManager`에는 update 메서드가 없음

```java
tx.begin();
Member member = em.find(Member.class, 1L);   // 영속
member.setName("새이름");                     // 값만 변경
// em.update(member) 같은 호출 없음
tx.commit();                                 // flush 때 변경 감지 → UPDATE 실행
```

- 감지 대상은 **영속 상태**만 → 준영속(detach)으로 만들거나 읽기 전용으로 표시하면 감지하지 않음
- 엔티티가 많으면 감지 비용이 커질 수 있음
- Spring Data JPA 문서: 트랜잭션 안에서 영속 엔티티를 고친 뒤 `save()` 호출은 **JPA 관점에선 꼭 필요하진 않음** (리포지터리 추상화 일관성 때문에 두는 것)
- Spring의 `@Transactional(readOnly = true)` + Hibernate → flush 모드가 `MANUAL`로 설정되어 **변경 감지를 건너뜀** (큰 객체 그래프에서 성능 이득)

### 삭제
- `remove()`된 엔티티는 삭제 상태가 되고, **트랜잭션 완료 또는 flush 때** DB에서 DELETE됨

## 플러시 (flush)

### 무엇인가
- **영속성 컨텍스트의 변경 내용을 DB에 동기화**하는 것 (JPA 명세 `flush()` 설명)
- 컨텍스트를 비우는 게 아님 → 비우는 건 `clear()`. flush 후에도 엔티티는 영속 상태 유지
- 트랜잭션이 있어야 함 → 트랜잭션 없이 `flush()` 호출 시 `TransactionRequiredException`
- cascade가 `PERSIST`/`ALL`이면 연관 엔티티도 함께 동기화

### 언제 일어나나

| 시점 | 설명 |
|---|---|
| **트랜잭션 커밋** | 커밋 시 영속 엔티티 상태가 DB에 동기화됨 |
| **`em.flush()` 직접 호출** | 강제로 즉시 동기화 |
| **JPQL 쿼리 실행** | flush 모드 `AUTO`(기본)일 때 쿼리 결과에 영향을 줄 수 있는 변경을 쿼리 전에 반영 |

```java
em.persist(memberA);
em.persist(memberB);
// 아래 JPQL은 DB에서 조회하므로, 아직 INSERT 안 된 A·B가 빠지면 안 됨
List<Member> list = em.createQuery("select m from Member m", Member.class)
                      .getResultList();   // AUTO → 쿼리 전에 반영되어 A·B 포함
```

### 플러시 모드 (`jakarta.persistence.FlushModeType`)

| 모드 | 동작 |
|---|---|
| `AUTO` (기본) | 쿼리 실행 시 플러시 — 쿼리 결과에 영향 줄 변경이 쿼리에 보이도록 보장 |
| `COMMIT` | 커밋 시 플러시 — 쿼리 전 변경 반영은 보장하지 않음 |

- 활성 트랜잭션이 없으면 구현체는 DB로 flush하면 안 됨
- `em.setFlushMode(...)`로 컨텍스트 전체에, 쿼리 객체에 따로 지정 가능

## 준영속 상태

### 준영속으로 만드는 방법

| 메서드 | 효과 |
|---|---|
| `em.detach(entity)` | 그 엔티티 하나만 컨텍스트에서 분리 |
| `em.clear()` | 컨텍스트를 통째로 비움 → 관리 중이던 모든 엔티티가 준영속 |
| `em.close()` | 컨텍스트 종료 → 관리 중이던 엔티티가 준영속 |

- `detach`·`clear` 전에 **flush 안 된 변경(삭제 포함)은 DB에 반영되지 않음**
- 분리된 엔티티를 참조하던 다른 엔티티는 그대로 그 객체를 참조함

```java
tx.begin();
Member member = em.find(Member.class, 1L);   // 영속
member.setName("바뀐이름");
em.detach(member);                           // 준영속 → 변경 감지 대상에서 빠짐
tx.commit();                                 // UPDATE 실행 안 됨
```

### 준영속의 특징
- 식별자(기본 키) 값은 있지만 컨텍스트가 관리하지 않음 → 1차 캐시·변경 감지·쓰기 지연 등 **아무 기능도 동작 안 함**
- **지연 로딩 불가**: 아직 안 가져온 연관 엔티티는 프록시로 있다가, 프록시가 **열린 세션과 연결돼 있을 때만** 접근 시 DB에서 로딩됨 → 준영속이면 실패. [연관관계 매핑 기초](03_연관관계_매핑_기초.md)의 위키독스 오류 사례가 이 경우
- 다시 관리하려면 `merge()` (Hibernate는 준영속 객체를 영속으로 옮기던 예전 메서드들을 모두 deprecated 처리하고 `merge()`를 쓰라고 함)

### 그 밖의 메서드

| 메서드 | 뜻 |
|---|---|
| `em.contains(entity)` | 현재 컨텍스트가 관리 중인 엔티티인지 |
| `em.refresh(entity)` | DB 값으로 다시 덮어씀 (메모리 변경은 버림) |
| `em.getReference(Class, pk)` | 상태를 나중에 가져올 수 있는 참조(프록시) 반환. 없는 데이터면 처음 접근할 때 `EntityNotFoundException` (구현체에 따라 호출 시점에 날 수도 있음) |

## 참고

- 영속성 컨텍스트는 엔티티를 강한 참조로 잡고 있어 GC되지 않음 → `EntityManager`/`Session`은 짧게 쓰고 논리적 트랜잭션이 끝나면 버려야 함. 아주 많은 엔티티를 읽는 배치성 작업은 `clear()`·`detach()`로 메모리를 조절하거나 Hibernate `StatelessSession` 사용
- 예외가 나면 트랜잭션을 롤백하고 그 `Session`도 폐기 → 예외 후 내부 상태는 DB와 일치한다고 볼 수 없음

## 면접 포인트

- **영속성 컨텍스트란?** 엔티티를 관리하는 논리적 공간으로, 같은 기본 키에 대해 인스턴스를 하나만 둠. EntityManager가 이를 통해 1차 캐시 조회, 동일성 보장, 쓰기 지연, 변경 감지를 제공함.
- **변경 감지(dirty checking)는 어떻게 동작?** 영속 상태 엔티티의 값 변경을 컨텍스트가 감지해 flush(보통 커밋) 때 UPDATE를 자동 실행함. 그래서 update 메서드가 없고, 준영속 엔티티는 감지되지 않음.
- **flush와 commit의 차이? flush가 일어나는 시점?** flush는 컨텍스트 변경을 DB에 SQL로 보내는 것이고 커밋은 트랜잭션을 확정하는 것. flush는 커밋 직전, `em.flush()` 호출, 그리고 기본 모드(AUTO)에서 JPQL 실행 전에 일어나며 컨텍스트를 비우지 않음.
- **준영속 상태의 문제?** 컨텍스트 관리 밖이라 변경 감지가 안 되고 지연 로딩 시 예외가 남. 다시 반영하려면 `merge()`로 영속 인스턴스에 복사해야 함.
