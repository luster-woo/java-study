## 연관관계가 필요한 이유

- 객체는 **참조**로 다른 객체를 가리키고, 테이블은 **외래 키(FK)** 컬럼으로 다른 테이블과 연결됨
- 두 엔티티의 연관관계는 보통 **한쪽 테이블의 외래 키 하나**로 매핑됨
- 답변 엔티티에 질문 FK 값(`Integer questionId`)만 들고 있으면, 답변의 질문 제목을 알기 위해 그 id로 질문을 **다시 조회**해야 함
- 대신 `Question question` **참조**를 두고 연관관계로 매핑하면 `answer.getQuestion().getSubject()`처럼 객체 그래프로 바로 접근

### 다중성과 방향

| 다중성 | 어노테이션 | 예 |
|---|---|---|
| 다대일 (N:1) | `@ManyToOne` | 답변 여러 개 → 질문 하나 |
| 일대다 (1:N) | `@OneToMany` | 질문 하나 → 답변 여러 개 |
| 일대일 (1:1) | `@OneToOne` | 보관함 하나 ↔ 물건 하나 |
| 다대다 (N:M) | `@ManyToMany` | 수강생 ↔ 강좌 (별도 연결 테이블) |

| 방향 | 뜻 |
|---|---|
| **단방향** | 한 엔티티만 상대를 참조 (A → B) |
| **양방향** | 서로 참조 (A ↔ B) |

- 방향은 **JPQL 탐색**에도 영향: 단방향 `LineItem → Product`면 쿼리에서도 LineItem에서 Product로만 따라갈 수 있음
- 가장 기본이고 가장 많이 쓰는 건 **다대일**. Hibernate 문서: 애매하면 `@ManyToOne` + `@OneToMany(mappedBy=...)` 조합으로 FK 관계를 매핑하라고 권함

## 단방향 연관관계 (N:1)

### 위키독스 예제 — 답변 → 질문

```java
package com.mysite.sbb;

import java.time.LocalDateTime;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.ManyToOne;
import lombok.Getter;
import lombok.Setter;

@Getter
@Setter
@Entity
public class Answer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Integer id;

    @Column(columnDefinition = "TEXT")
    private String content;

    private LocalDateTime createDate;

    @ManyToOne                  // 답변(N) → 질문(1)
    private Question question;  // DB에서는 answer 테이블의 FK 컬럼
}
```

- `question` 필드만 두면 안 되고 `@ManyToOne`으로 **질문 엔티티와 연결된 속성**임을 표시해야 함 → DB에 외래 키 관계가 생성됨
- 위키독스 표현: 부모(Question)–자식(Answer) 구조에서 자식 쪽에 `@ManyToOne`

### FK 컬럼 이름
- 기본 규칙(JPA 명세): **연관 필드 이름 + `_` + 상대 테이블 PK 컬럼 이름** → `question` + `_` + `id` = `question_id`
- 바꾸려면 `@JoinColumn`

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "question_id")   // FK 컬럼 이름 지정
private Question question;
```

### 사용 — 저장과 조회

```java
// 저장: 답변에 질문을 연결 (위키독스 AnswerService.create)
Answer answer = new Answer();
answer.setContent(content);
answer.setCreateDate(LocalDateTime.now());
answer.setQuestion(question);      // 참조를 넣으면 JPA가 FK 값으로 저장
answerRepository.save(answer);

// 조회: 답변 → 질문 바로 탐색
Answer a = answerRepository.findById(1).get();
Integer qid = a.getQuestion().getId();
```

## 양방향 연관관계

### 질문 → 답변 목록도 필요할 때

```java
package com.mysite.sbb;

import java.time.LocalDateTime;
import java.util.List;

import jakarta.persistence.CascadeType;
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.OneToMany;

import lombok.Getter;
import lombok.Setter;

@Getter
@Setter
@Entity
public class Question {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Integer id;

    @Column(length = 200)
    private String subject;

    @Column(columnDefinition = "TEXT")
    private String content;

    private LocalDateTime createDate;

    @OneToMany(mappedBy = "question", cascade = CascadeType.REMOVE)
    private List<Answer> answerList;    // 질문(1) → 답변(N)
}
```

- 질문 하나에 답변 여러 개 → `List<Answer>`로, `@OneToMany`
- `mappedBy = "question"`: **상대 엔티티(Answer)에서 나를 참조하는 필드 이름** → `Answer.question`
- 이제 `question.getAnswerList()`로 질문의 답변들에 접근

### 테이블은 그대로
- 단방향 → 양방향으로 바꿔도 **테이블에는 변화 없음**: FK는 여전히 `answer.question_id` 하나
- 테이블은 FK 하나로 양쪽 조인이 되지만, 객체는 참조가 한 방향이라 서로 탐색하려면 양쪽에 필드를 하나씩 둬야 함

```
객체                                   테이블
Question.answerList  ─┐               QUESTION (id, subject, content, create_date)
                      │ 양방향           ▲
Answer.question  ◀───┘               ANSWER (id, content, create_date, question_id FK)
```

## 연관관계의 주인 (owning side)

### 왜 주인이 필요한가
- 양방향이면 FK를 바꿀 수 있는 곳이 두 군데처럼 보임: `answer.setQuestion(q)` vs `q.getAnswerList().add(answer)`
- FK 컬럼은 하나 → **둘 중 하나만 DB의 관계(FK)를 관리**해야 함 → 그쪽이 **연관관계의 주인**
- 주인 쪽이 **런타임이 DB의 관계를 어떻게 갱신할지** 결정함 (단방향은 주인만 있음)

### 규칙 (JPA 명세·Jakarta 튜토리얼)

| 규칙 | 내용 |
|---|---|
| 주인이 아닌 쪽(inverse)은 `mappedBy` | `@OneToOne`·`@OneToMany`·`@ManyToMany`의 `mappedBy`로 **주인 필드**를 가리킴 |
| N:1 / 1:N 양방향의 주인 = **N(다) 쪽** | 항상 다 쪽이 주인 → **`@ManyToOne`에는 `mappedBy` 속성 자체가 없음** |
| 1:1 양방향의 주인 | **외래 키가 있는 쪽** |
| N:M 양방향 | 어느 쪽이든 주인 가능 |
| 매핑 세부 지정 | `@JoinColumn` 같은 FK 매핑 어노테이션은 **주인 쪽**에 |

- 정리: **외래 키가 있는 테이블의 엔티티 = 주인** → SBB에서는 `Answer.question`이 주인, `Question.answerList`는 읽기 전용(조회용)

### 주인이 아닌 쪽만 바꾸면 반영 안 됨
- Hibernate 문서: 주인이 아닌 쪽에 한 변경은 **DB에 절대 동기화되지 않음** → DB의 관계를 바꾸려면 주인 쪽(`Answer.question`)을 바꿔야 함

```java
// question은 트랜잭션 안에서 조회한 영속 엔티티라고 가정
Answer answer = new Answer();
answer.setContent("답변");
question.getAnswerList().add(answer);   // 주인 아님 → FK에 반영 안 됨
answerRepository.save(answer);          // answer.question_id = null 로 저장

answer.setQuestion(question);           // 주인 → 이 값으로 FK 저장
```

## 양방향 매핑 시 주의점

### 1. 양쪽 값을 다 맞춰 두기
- DB 반영은 주인만 보지만, JPA 명세는 **런타임에 양방향 관계의 양쪽을 일관되게 유지할 책임은 애플리케이션에 있다**고 함
- 주인만 설정하면, 같은 트랜잭션 안에서 아직 DB를 다시 읽지 않은 `question.getAnswerList()`에는 새 답변이 안 보일 수 있음
- Hibernate 문서도 2차 캐시 등을 쓰면 **양쪽을 함께 바꾸는 것이 필요한 경우가 많다**고 함
- 해결: 한 메서드에서 양쪽을 같이 세팅하는 **연관관계 편의 메서드**

```java
import java.util.ArrayList;
import java.util.List;

public class BidirectionalTest {
    static class Question {
        String subject;
        List<Answer> answerList = new ArrayList<>();
        Question(String subject) { this.subject = subject; }
    }

    static class Answer {
        String content;
        Question question;   // 연관관계의 주인(FK를 가진 쪽)
        Answer(String content) { this.content = content; }

        // 연관관계 편의 메서드: 양쪽을 한 번에 맞춘다
        void changeQuestion(Question q) {
            if (this.question != null) {
                this.question.answerList.remove(this);
            }
            this.question = q;
            q.answerList.add(this);
        }
    }

    public static void main(String[] args) {
        Question q = new Question("sbb가 무엇인가요?");

        Answer a1 = new Answer("네 자동으로 생성됩니다.");
        a1.question = q;                              // 주인 쪽만 설정
        System.out.println(q.answerList.size());      // 0

        Answer a2 = new Answer("따로 생성할 필요가 없습니다.");
        a2.changeQuestion(q);                         // 양쪽 모두 설정
        System.out.println(q.answerList.size());      // 1
        System.out.println(a2.question.subject);      // sbb가 무엇인가요?
    }
}
```

- 순수 자바 객체로만 보면 주인 쪽만 세팅한 `a1`은 질문의 답변 목록에 없음 → 객체 상태와 DB 상태가 어긋남
- 위키독스 SBB의 `AnswerService.create`는 주인(`answer.setQuestion`)만 세팅하고 저장 → 저장 후 **redirect된 새 요청**에서 질문을 다시 조회하므로 상세 화면의 답변 목록에는 정상 표시됨

### 2. 컬렉션은 인터페이스 타입으로 선언
- Hibernate는 아직 안 가져온 연관을 런타임에 **프록시(래퍼)** 로 바꿔 넣음 → 필드 타입은 `List`·`Set`·`Collection` 같은 **인터페이스**로, `ArrayList`·`HashSet` 같은 구현 타입으로 선언하지 않음
- `Set`을 쓰면 원소 엔티티의 `equals()`/`hashCode()` 구현에 민감해짐 → `List`/`Collection`도 무방 (Hibernate 문서)
- DB에서 조회한 엔티티에 연관된 엔티티가 없으면 JPA가 `null`이 아니라 빈 컬렉션을 돌려줌

### 3. 페치 전략 기본값 주의

| 어노테이션 | 기본 `fetch` |
|---|---|
| `@ManyToOne`, `@OneToOne` | `EAGER` (즉시 로딩) |
| `@OneToMany`, `@ManyToMany` | `LAZY` (지연 로딩) |

- Hibernate 문서: `@ManyToOne`이 기본 EAGER인 건 JPA의 불행한 설계 → **거의 모든 연관은 LAZY가 맞으므로** `@ManyToOne(fetch = FetchType.LAZY)`를 명시하라고 권함
- 지연 로딩 = 연관 객체를 처음엔 프록시로 두고 **실제로 접근할 때** 조회

### 4. 지연 로딩과 영속성 컨텍스트 범위 (위키독스 오류 사례)

```java
// import 생략 (Optional, List, assertEquals/assertTrue, org.springframework.transaction.annotation.Transactional 등)
@SpringBootTest
class SbbApplicationTests {

    @Autowired
    private QuestionRepository questionRepository;

    @Transactional          // 없으면 q.getAnswerList() 사용 시 오류
    @Test
    void testJpa() {
        Optional<Question> oq = this.questionRepository.findById(2);
        assertTrue(oq.isPresent());
        Question q = oq.get();

        List<Answer> answerList = q.getAnswerList();   // 지연 로딩 대상

        assertEquals(1, answerList.size());
        assertEquals("네 자동으로 생성됩니다.", answerList.get(0).getContent());
    }
}
```

- `@Transactional` 없이 실행하면 `answerList`를 쓰는 지점에서 오류 → 위키독스 설명: `findById`로 질문을 가져온 뒤 **DB 세션이 끊어지고**, `answerList`는 조회 때가 아니라 `getAnswerList()`를 쓰는 시점에 가져오는 **지연(Lazy) 방식**이라서
- 공식 문서 용어로 보면
  - Spring Data JPA의 `findById` 같은 CRUD 메서드는 **메서드마다 자체 트랜잭션**(조회는 readOnly)으로 실행됨
  - 프록시는 **열린 세션(영속성 컨텍스트)과 연결돼 있을 때만** 접근 시 로딩됨 (Hibernate `Session` javadoc) → 메서드가 끝나 연결이 없으면 로딩 실패
- 테스트 메서드에 `@Transactional`(`org.springframework.transaction.annotation`) → 메서드 끝까지 세션 유지 → 정상 동작
- 위키독스: 실제 서버 실행 시에는 이 오류가 안 남 → Spring Boot는 웹 애플리케이션에서 기본으로 **Open EntityManager in View**(`OpenEntityManagerInViewInterceptor`)를 등록해 뷰에서의 지연 로딩을 허용함. 끄려면 `spring.jpa.open-in-view=false`

### 5. cascade와 orphanRemoval
- 위키독스 `cascade = CascadeType.REMOVE`: **질문을 삭제하면 달린 답변도 함께 삭제** (게시판의 일반적 동작)

| CascadeType | 부모에 이 연산을 하면 연관 엔티티에도 |
|---|---|
| `PERSIST` | persist |
| `MERGE` | merge |
| `REMOVE` | remove |
| `REFRESH` | refresh |
| `DETACH` | detach |
| `ALL` | 위 전부 |

- `cascade=REMOVE`는 `@OneToOne`·`@OneToMany`에만 쓰는 것이 이식성 있음 (다른 연관에 쓰면 비표준)
- `orphanRemoval = true` (`@OneToOne`·`@OneToMany`, 기본 false): 컬렉션에서 빼거나 참조를 `null`로 만든 **고아 엔티티를 flush 때 삭제** → 부모가 "소유"하는 자식에만

### 6. 단방향 @OneToMany는 피하기
- `@ManyToOne` 없이 `@OneToMany`만 두는 단방향 일대다는 Hibernate가 허용하긴 하지만 **부자연스럽고 잘 동작하지 않음** → Hibernate 문서가 피하라고 함

## 참고

- Hibernate 문서는 `mappedBy = "question"` 같은 문자열 대신 메타모델 생성기가 만드는 상수(`mappedBy = Answer_.QUESTION`)를 쓰면 오타를 컴파일 시점에 잡을 수 있다고 소개함
- 일대일은 FK 컬럼에 `UNIQUE` 제약이 붙은 다대일과 거의 같음. 주인이 아닌 쪽 `@OneToOne`은 FK가 상대 테이블에 있어 `null` 여부를 알려면 조회가 필요하므로 지연 로딩이 잘 안 됨
- 다대다는 항상 별도 연결 테이블로 매핑되고, Hibernate 문서는 다대다가 결국 "엔티티가 숨어 있는" 경우가 많다고 함

## 면접 포인트

- **연관관계의 주인이란?** 양방향 관계에서 외래 키를 실제로 관리(등록·수정)하는 쪽. 외래 키가 있는 테이블의 엔티티, 즉 N:1에서는 `@ManyToOne` 쪽이 주인이고 반대쪽은 `mappedBy`로 읽기 전용이 됨.
- **`mappedBy`는 무엇을 적나?** 주인이 아닌 쪽에서, 상대(주인) 엔티티가 나를 참조하는 필드 이름을 적음. 예: `@OneToMany(mappedBy = "question")`.
- **양방향 매핑 주의점?** 주인 쪽에 값을 넣어야 FK가 저장되고, 객체 상태 일관성을 위해 양쪽 모두 세팅(편의 메서드)해야 함. 또 `@ManyToOne` 기본 EAGER는 LAZY로 바꾸는 게 권장됨.
- **지연 로딩 시 LazyInitialization 계열 오류가 나는 이유?** 프록시가 영속성 컨텍스트(세션)가 닫힌 뒤 초기화를 시도하기 때문. 트랜잭션 범위 안에서 접근하거나 필요한 데이터를 미리 조회해야 함.
