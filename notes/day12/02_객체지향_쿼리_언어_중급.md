## 경로 표현식

### 정의

- **경로 표현식(path expression)**: `.`(점)으로 엔티티 속성을 따라가는 표현
  - 식별 변수(별칭) 하나만 쓴 것: `book`
  - 식별 변수 + `.`으로 이은 속성들: `book.publisher.name`
- 경로 중간에 **연관관계**가 있으면 SQL에 **묵시적 조인(implicit join)**이 생김

```sql
select book.publisher.name from Book book   -- Book → Publisher 조인이 SQL에 추가됨
```

### 속성 종류에 따른 탐색 규칙

| 경로가 가리키는 속성 | 더 탐색 가능? | 예 |
|---|---|---|
| 기본 타입 값 (상태 필드) | X — 경로의 **끝** | `book.title` |
| 임베디드 타입 / `~ToOne` 연관 (단일 값 연관) | O — 계속 `.`으로 이어 감 | `book.publisher.name` |
| 컬렉션 / `~ToMany` 연관 (컬렉션 값 연관) | **바로는 X** — `book.authors.name`은 문법 오류 | 명시적 `join`으로 별칭을 얻어 탐색 (HQL은 `element(book.authors).name`도 허용) |

```sql
-- 컬렉션은 명시적 조인으로 별칭을 만든 뒤 탐색
select publisher.name, author.name
from Publisher publisher
    join publisher.books book
    join book.authors author
where author.name like :namePattern
```

- 컬렉션 조인의 별칭은 **컬렉션의 원소**를 가리킴 (`Set`·`List`의 원소, `Map`의 값)

### 묵시적 조인의 특징

- 항상 **inner join**으로 처리
- 같은 경로를 여러 번 써도 **SQL 조인은 하나**
- JPQL의 `from` 절 밖(select·where)에 써도 SQL의 `from` 절에는 항상 조인이 추가됨 → 쿼리만 보고는 조인이 몇 개인지 알기 어려움

```sql
-- 묵시적 조인
select book from Book book
where book.publisher.name like :pubName

-- 위와 같은 의미의 명시적 조인
select book from Book book
    join book.publisher pub
where pub.name like :pubName
```

### 명시적 조인 종류

| 문법 | 의미 |
|---|---|
| `join`, `inner join` | 내부 조인 |
| `left join`, `left outer join` | 왼쪽 외부 조인 — 연관 대상이 없어도 기준 엔티티는 결과에 포함 |
| `right join`, `full join` | 오른쪽·완전 외부 조인 |
| `join ... on 조건` | FK 조인 조건에 **추가** 조건을 붙임 (`on`은 JPQL, `with`는 Hibernate 전용) |

## fetch join

### 개념

- 연관관계의 **지연 로딩 설정을 덮어쓰고** SQL 조인 한 번으로 연관 엔티티까지 함께 가져오는 조인
- Hibernate 문서: HQL에서 성능을 내려면 자주 써야 하고, 쓰지 않으면 곧 **"n+1 selects" 문제**를 만남

| 문법 | 결과 |
|---|---|
| `join fetch` (`inner join fetch`) | 연관 엔티티가 **있는** 기준 엔티티만 |
| `left join fetch` | 연관 엔티티가 없는 기준 엔티티도 포함 |

```sql
select m from Member m join fetch m.team          -- 회원 + 팀을 한 번에
select t from Team t left join fetch t.members    -- 팀 + 회원 컬렉션을 한 번에
```

### 일반 join과 fetch join의 차이

| | 일반 `join` | `join fetch` |
|---|---|---|
| SQL | 조인은 함 | 조인함 + 연관 엔티티 컬럼도 select |
| 결과에 채워지는 것 | **select 절에 쓴 엔티티만** | select 엔티티 + 연관 엔티티(프록시가 아닌 실제 엔티티) |
| 연관 컬렉션 | 초기화 안 된 컬렉션 → 접근하면 지연 로딩 → **N+1 그대로** | 이미 채워져 있음 → 추가 쿼리 없음 |

- 일반 조인은 연관 대상을 **조건 거는 용도**, fetch join은 **함께 가져오는 용도**

### fetch join 사용 시 주의

- **여러 개 fetch join**
  - `~ToOne` 연관 여러 개를 함께 fetch → 안전
  - 한 줄로 이어진 **중첩** fetch (`a.b.c`) → 괜찮음
  - **컬렉션 여러 개를 나란히** fetch → DB에서 카테시안 곱 → 성능이 매우 나빠질 수 있음
  - Hibernate는 `List`(bag) 컬렉션 둘을 동시에 fetch하면 "cannot simultaneously fetch multiple bags" 예외 — `Set`으로 바꾸면 예외는 사라지지만 예외를 피하려고 도메인의 자료형을 바꾸는 것은 좋은 해결이 아님 (Popit)
- **fetch join 대상에 where 조건 X** — 가져온 컬렉션의 원소가 일부만 채워진 상태가 됨. fetch 대상 별칭은 중첩 fetch를 쓸 때만
- **페이징과 함께 쓰지 않기** — `setFirstResult()`/`setMaxResults()`, HQL의 `limit`/`offset`, `scroll()`/`stream()`
  - 컬렉션을 fetch join하고 페이징 API를 쓰면 Hibernate가 SQL에 limit을 붙이지 않고 **전체를 메모리에 올린 뒤 메모리에서 페이징** → 메모리 위험 (Popit)
  - `~ToOne`(단일 값 연관) fetch join은 페이징과 함께 써도 됨 (Popit) — Hibernate 문서는 페이징 쿼리에서 fetch join을 "보통 피하라"고 넓게 권고하므로, 컬렉션 fetch가 특히 문제라고 이해하면 됨
- 서브쿼리 안에서는 fetch join 불가

## N+1 문제

### 무엇인가

- 목록 조회 쿼리 **1번** + 결과 N건 각각의 연관 데이터를 가져오는 쿼리 **N번**이 나가는 문제

### 원인

- `findById()`(= `em.find`)는 영속성 컨텍스트를 먼저 보지만 **JPQL은 항상 DB에 SQL을 실행**
  1. JPQL을 SQL로 바꿔 DB 조회
  2. 결과를 영속성 컨텍스트에 저장 (이미 있는 엔티티면 조회 결과를 버림)
- JPQL은 엔티티에 설정한 **글로벌 fetch 전략(EAGER/LAZY)을 무시**하고 JPQL 그대로 SQL을 만듦 → `findAll()`은 `select * from member` 한 번

| fetch 설정 | 무슨 일이 일어나나 |
|---|---|
| `EAGER` | 결과를 받은 뒤 즉시 로딩 설정을 적용 → 회원마다 주문을 조회 → **바로 N+1** |
| `LAZY` | 그 순간엔 추가 쿼리 없음. 하지만 반복문에서 `member.getOrders()`에 접근하면 회원마다 조회 → **결국 N+1** |

- LAZY로 바꾸는 것만으로는 해결되지 않고 **쿼리가 나가는 시점만 미뤄짐**

### 예제 — 순수 자바로 쿼리 수 세어 보기

```java
import java.util.ArrayList;
import java.util.List;

public class NPlusOneDemo {
    static int queries = 0;

    static void sql(String s) {
        queries++;
        System.out.println("  " + s);
    }

    public static void main(String[] args) {
        int n = 5;   // 회원 5명

        System.out.println("1) 지연 로딩 + 반복문에서 orders 접근");
        queries = 0;
        sql("select * from member");                       // findAll()
        for (int id = 1; id <= n; id++) {
            sql("select * from orders where member_id = " + id); // 회원마다 1번
        }
        System.out.println("  쿼리 수 = " + queries);     // 1 + N

        System.out.println("2) fetch join");
        queries = 0;
        sql("select m.*, o.* from member m left join orders o on o.member_id = m.id");
        System.out.println("  쿼리 수 = " + queries);

        System.out.println("3) batch size = 2");
        queries = 0;
        sql("select * from member");
        int batch = 2;
        for (int start = 1; start <= n; start += batch) {
            List<Integer> ids = new ArrayList<>();
            for (int id = start; id < start + batch && id <= n; id++) ids.add(id);
            sql("select * from orders where member_id in " + ids);
        }
        System.out.println("  쿼리 수 = " + queries);     // 1 + ceil(N / batch)
    }
}
/* 출력
1) 지연 로딩 + 반복문에서 orders 접근
  select * from member
  select * from orders where member_id = 1
  select * from orders where member_id = 2
  select * from orders where member_id = 3
  select * from orders where member_id = 4
  select * from orders where member_id = 5
  쿼리 수 = 6
2) fetch join
  select m.*, o.* from member m left join orders o on o.member_id = m.id
  쿼리 수 = 1
3) batch size = 2
  select * from member
  select * from orders where member_id in [1, 2]
  select * from orders where member_id in [3, 4]
  select * from orders where member_id in [5]
  쿼리 수 = 4
*/
```

- 실제 JPA가 아니라 각 방법에서 **SQL이 몇 번, 어떤 모양으로 나가는지**만 흉내 낸 것

### 해결 1 — fetch join

```java
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import java.util.List;

public interface MemberRepository extends JpaRepository<Member, Long> {

    @Query("select m from Member m left join fetch m.orders")
    List<Member> findAllWithOrders();   // 회원 + 주문을 쿼리 1번으로
}
```

- 가장 많이 쓰는 방법. 단 위의 **주의사항**(컬렉션 + 페이징, 컬렉션 2개 이상)에 걸림

### 해결 2 — @EntityGraph (Spring Data JPA)

- JPA 2.1의 fetch graph / load graph를 리포지토리 메서드에 선언하는 방법 → 쿼리의 **fetch plan**(무엇을 같이 가져올지)을 지정
- JPQL을 직접 쓰지 않고 메서드 이름 쿼리에도 붙일 수 있음

```java
import org.springframework.data.jpa.repository.EntityGraph;

public interface MemberRepository extends JpaRepository<Member, Long> {

    @EntityGraph(attributePaths = {"orders"})   // 즉석(ad hoc) 엔티티 그래프
    List<Member> findByName(String name);
}
```

```java
// 엔티티에 이름 붙은 그래프를 정의하고 참조하는 방법
@Entity
@NamedEntityGraph(name = "Member.orders",
        attributeNodes = @NamedAttributeNode("orders"))
public class Member { ... }

public interface MemberRepository extends JpaRepository<Member, Long> {

    @EntityGraph(value = "Member.orders", type = EntityGraph.EntityGraphType.LOAD)
    List<Member> findByName(String name);
}
```

- `type` 속성으로 `FETCH`/`LOAD` 중 선택

### 해결 3 — batch size

- 지연 로딩은 그대로 두고, 아직 가져오지 않은 프록시·컬렉션을 **`where ... in (id1, id2, ...)`으로 묶어서** 가져오는 방식
  - 기본 키 하나로 조회하는 대신 `in` 조건에 여러 기본 키를 넣음
  - 묶을 키는 **현재 세션에 있는 미초기화 프록시·컬렉션**에서 고름
- 쿼리 수: `1 + ceil(N / size)`

```java
import org.hibernate.annotations.BatchSize;

@Entity
@BatchSize(size = 100)      // 미초기화 Member 프록시를 한 번에 최대 100개씩 초기화
public class Member { ... }

@Entity
public class Team {
    @OneToMany(mappedBy = "team")
    @BatchSize(size = 5)    // 미초기화 members 컬렉션을 한 번에 최대 5개(팀 5개분)씩
    private List<Member> members = new ArrayList<>();
}
```

- 전역 설정: `hibernate.default_batch_fetch_size` (`FetchSettings.DEFAULT_BATCH_FETCH_SIZE`) — 설정하지 않으면 `@BatchSize`를 붙인 곳에서만 batch fetching

```properties
# Spring Boot (application.properties)
spring.jpa.properties.hibernate.default_batch_fetch_size=100
```

### 해결 방법 비교

| 방법 | 쿼리 수 | 장점 | 주의 |
|---|---|---|---|
| fetch join | 1 | 원하는 쿼리에서 한 번에 가져옴 | 컬렉션 fetch + 페이징 X, 컬렉션 여러 개 동시 fetch X |
| `@EntityGraph` | (fetch plan으로 함께 조회) | JPQL 없이 메서드에 선언 | 그래프에 넣은 연관관계를 함께 가져온다는 점은 fetch join과 같음 |
| batch size | 1 + ceil(N/size) | 기준 쿼리에 조인이 없어 페이징 쿼리에 그대로 쓸 수 있음 | 쿼리가 1번으로 줄지는 않음 |

## 면접 포인트

- **N+1 문제란, 왜 생기나?** — 목록 1번 조회 후 각 결과의 연관 데이터를 N번 더 조회하는 문제. JPQL은 fetch 전략을 무시하고 쿼리대로 SQL을 만들기 때문에, EAGER면 조회 직후에, LAZY면 연관 데이터에 접근하는 순간 건마다 추가 쿼리가 나감.
- **해결 방법은?** — fetch join(쿼리 1번), `@EntityGraph`(메서드에 fetch plan 선언), batch size(`in` 절로 묶어 1+N/size번). 컬렉션을 페이징해야 하면 fetch join 대신 batch size를 씀.
- **fetch join과 일반 join 차이** — 일반 join은 select 절의 엔티티만 채우므로 연관 컬렉션은 여전히 지연 로딩되고, fetch join은 연관 엔티티까지 실제 객체로 채워 추가 쿼리가 없음.
- **컬렉션 fetch join에 페이징을 쓰면?** — Hibernate가 DB에서 limit 없이 전부 가져와 메모리에서 페이징하므로 데이터가 많으면 메모리 문제가 생김. `~ToOne` fetch join은 페이징해도 됨.
