## 프록시

### em.find() vs em.getReference()

| 메서드 | 동작 | 대상이 DB에 없으면 |
|---|---|---|
| `find(Team.class, id)` | 영속성 컨텍스트에 있으면 거기서 반환, 없으면 DB 조회 | `null` 반환 |
| `getReference(Team.class, id)` | **상태를 나중에 가져와도 되는** 인스턴스 반환 (DB 조회를 미룰 수 있음) | 상태에 처음 접근할 때 `EntityNotFoundException` (구현체가 `getReference` 호출 시점에 던져도 됨) |

- `getReference`로 받은 객체는 EntityManager가 열려 있을 때 접근한 적 없는 상태를 **detach 이후에 쓸 수 있다고 기대하면 안 됨**

### 프록시 객체의 특징 (Hibernate, 바이트코드 향상을 안 쓸 때)

- 아직 가져오지 않은 지연 연관관계는 **프록시 객체**로 채워짐 → 연관 엔티티의 **식별자(FK 값)만** 들고 있음
- **식별자 getter**는 프록시를 초기화하지 않음 → `team.getId()`는 쿼리 없음
- 그 외 메서드를 호출하는 순간 실제 엔티티(delegate)를 DB에서 가져옴 → 이후 모든 호출을 실제 객체에 **위임**
- 프록시는 실제 엔티티와 **구체 타입이 다름**
  - `obj.getClass()` 대신 `Hibernate.getClass(obj)` 사용 (이 메서드는 부수효과로 프록시를 초기화함)
  - 상속 관계 연관(다형성)은 실제 타입을 DB에서 가져오기 전까지 모름 → 형변환은 `Hibernate.unproxy(obj, X.class)`, `instanceof` 대신 `Hibernate.getClass()`
- 빌드 시점 바이트코드 향상을 켜면 프록시 대신 "식별자만 채워진 미로딩 상태의 실제 엔티티"를 씀 → 형변환·`instanceof`·`getClass()`를 그대로 써도 됨 (단, 다형 연관관계는 여전히 프록시 방식)

```
 member.team ─► TeamProxy (Team과 다른 클래스)
               ┌──────────────────────┐
               │ id = 1  (처음부터 보유)  │
               │ target = null ───────┼──► (getName() 첫 호출 시 DB 조회)
               └──────────────────────┘              │
                                                     ▼
                                          Team 엔티티 { id=1, name="개발팀" }
```

### 프록시 확인·초기화 유틸리티 (`org.hibernate.Hibernate`)

| 메서드 | 하는 일 |
|---|---|
| `Hibernate.isInitialized(obj)` | 프록시·지연 컬렉션이 초기화됐는지 확인 (JPA 표준 `PersistenceUtil.isLoaded(obj)`와 같음) |
| `Hibernate.initialize(obj)` | 강제 초기화. 컬렉션이면 **컬렉션 자체만** 초기화 — 안의 엔티티까지 초기화된다는 보장은 없음 |
| `Hibernate.getClass(obj)` | 프록시가 감싼 실제 클래스 반환 (초기화 발생) |
| `Hibernate.unproxy(obj)` | 프록시면 초기화 후 실제 엔티티 참조를 반환 |

### LazyInitializationException

- 열린 세션(영속성 컨텍스트) **밖에서** 아직 가져오지 않은 데이터에 접근할 때 발생
  - 예: 세션이 닫힌 뒤 초기화 안 된 프록시나 컬렉션에 접근
- `Hibernate.initialize()`도 세션이 닫혔으면 초기화하지 못하고 `HibernateException`을 던짐
- `unproxy()`도 열린 세션에 연결되지 않은 미초기화 프록시에 쓰면 `LazyInitializationException`
- 결국 **세션이 열려 있을 때(트랜잭션 안에서)** 필요한 연관관계를 미리 가져와야 함 → 방법은 [fetch join](02_객체지향_쿼리_언어_중급.md)

### 예제 — 순수 자바로 흉내 낸 지연 로딩 프록시

```java
import java.util.HashMap;
import java.util.Map;

public class LazyProxyDemo {
    public static void main(String[] args) {
        FakeDb db = new FakeDb();
        db.put(new RealTeam(1L, "개발팀"));

        Team team = new TeamProxy(1L, db);   // getReference()처럼 id만 가진 가짜 객체
        System.out.println("프록시 생성, 쿼리 수 = " + db.queryCount);
        System.out.println("id = " + team.getId() + ", 쿼리 수 = " + db.queryCount);
        System.out.println("name = " + team.getName() + ", 쿼리 수 = " + db.queryCount);
        System.out.println("name = " + team.getName() + ", 쿼리 수 = " + db.queryCount);
        System.out.println("클래스 = " + team.getClass().getSimpleName());
    }
}

interface Team {
    Long getId();
    String getName();
}

class RealTeam implements Team {
    private final Long id;
    private final String name;
    RealTeam(Long id, String name) { this.id = id; this.name = name; }
    public Long getId() { return id; }
    public String getName() { return name; }
}

class TeamProxy implements Team {
    private final Long id;          // 식별자는 처음부터 가지고 있음
    private final FakeDb db;
    private RealTeam target;        // 실제 엔티티(아직 null)

    TeamProxy(Long id, FakeDb db) { this.id = id; this.db = db; }

    public Long getId() { return id; }   // id 조회는 초기화하지 않음

    public String getName() {
        if (target == null) {            // 처음 쓸 때 한 번만 DB 조회
            target = db.find(id);
        }
        return target.getName();         // 이후에는 실제 객체에 위임
    }
}

class FakeDb {
    private final Map<Long, RealTeam> table = new HashMap<>();
    int queryCount = 0;
    void put(RealTeam t) { table.put(t.getId(), t); }
    RealTeam find(Long id) {
        queryCount++;
        System.out.println("  select * from team where id = " + id);
        return table.get(id);
    }
}
/* 출력
프록시 생성, 쿼리 수 = 0
id = 1, 쿼리 수 = 0
  select * from team where id = 1
name = 개발팀, 쿼리 수 = 1
name = 개발팀, 쿼리 수 = 1
클래스 = TeamProxy
*/
```

- 마지막 줄처럼 프록시의 클래스는 실제 엔티티 클래스와 다름 → 타입 비교에 `==`/`getClass()`를 쓰면 안 되는 이유
- 실제 Hibernate 프록시는 Hibernate가 런타임에 만든 클래스이며, 이 예제는 동작 원리만 흉내 낸 것

## 즉시 로딩과 지연 로딩

### FetchType

| 값 | 의미 |
|---|---|
| `EAGER` (즉시) | 연관 데이터를 **반드시** 즉시 가져와야 함 — 구현체가 지켜야 하는 요구사항 |
| `LAZY` (지연) | 처음 접근할 때 가져와도 됨 — 구현체에 주는 **힌트**라서 즉시 가져와도 규칙 위반은 아님 |

### 연관관계 어노테이션별 기본값

| 어노테이션 | `fetch` 기본값 |
|---|---|
| `@ManyToOne` | **EAGER** |
| `@OneToOne` | **EAGER** |
| `@OneToMany` | LAZY |
| `@ManyToMany` | LAZY |

- 정리: **`~ToOne`은 즉시, `~ToMany`는 지연**이 기본

### 거의 모든 연관관계는 LAZY로

- Hibernate 문서: `@ManyToOne`이 기본으로 즉시 로딩되는 것은 JPA의 불행한 설계이고, 거의 원하는 동작이 아님
  - EAGER가 맞는 경우는 연관 객체가 2차 캐시에 있을 확률이 아주 높을 때 정도
  - 그 외에는 `fetch = LAZY`를 **명시**
- 함께 필요할 때만 쿼리에서 같이 가져옴 → [fetch join, @EntityGraph](02_객체지향_쿼리_언어_중급.md)

```java
import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.List;

@Entity
public class Member {
    @Id @GeneratedValue
    private Long id;

    private String name;

    @ManyToOne(fetch = FetchType.LAZY)   // 기본 EAGER → LAZY로 명시
    @JoinColumn(name = "team_id")
    private Team team;
}

@Entity
public class Team {
    @Id @GeneratedValue
    private Long id;

    private String name;

    @OneToMany(mappedBy = "team")       // 기본이 LAZY
    private List<Member> members = new ArrayList<>();
}
```

- 컬렉션 필드는 `List`·`Set` 같은 **인터페이스 타입**으로 선언 — Hibernate가 아직 가져오지 않은 컬렉션을 자기 컬렉션 구현으로 바꿔 끼우기 때문 (`ArrayList`·`HashSet` 타입으로 선언 X)
- `@OneToOne`의 반대쪽(`mappedBy` 쪽)은 LAZY가 잘 안 먹는 경우가 있음 → [다양한 연관관계 매핑](03_다양한_연관관계_매핑.md)의 일대일 절

## 영속성 전이: CASCADE

### 개념

- 어떤 엔티티에 한 **영속성 연산을 연관 엔티티에도 전파**할지 정하는 설정
- `@ManyToOne`·`@OneToMany`·`@OneToOne`·`@ManyToMany` 모두 `cascade` 속성 보유, 기본값 `{}` = **아무 연산도 전파하지 않음**

### CascadeType

| 값 | 전파하는 연산 |
|---|---|
| `PERSIST` | 저장 (`persist`) |
| `MERGE` | 병합 (`merge`) |
| `REMOVE` | 삭제 (`remove`) |
| `REFRESH` | 새로고침 (`refresh`) |
| `DETACH` | 준영속화 (`detach`) |
| `ALL` | 위 다섯 개 전부 — `{PERSIST, MERGE, REMOVE, REFRESH, DETACH}`와 같음 |

### 예제 — 부모 저장 시 자식도 저장

```java
@Entity
public class Parent {
    @Id @GeneratedValue
    private Long id;

    @OneToMany(mappedBy = "parent", cascade = CascadeType.ALL)
    private List<Child> children = new ArrayList<>();

    public void addChild(Child child) {   // 양쪽을 함께 세팅하는 편의 메서드
        children.add(child);
        child.setParent(this);            // FK를 관리하는 쪽(주인)을 반드시 세팅
    }
}

@Entity
public class Child {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "parent_id")
    private Parent parent;

    public void setParent(Parent parent) { this.parent = parent; }
}
```

```java
Parent parent = new Parent();
parent.addChild(new Child());
parent.addChild(new Child());

em.persist(parent);   // cascade=PERSIST가 포함돼 있어 Child 2개도 함께 persist
```

- cascade는 **"어떤 연산을 같이 적용하나"**만 정함
- **FK를 누가 관리하나**(연관관계의 주인, `mappedBy`)는 별개 — 주인이 아닌 쪽 컬렉션만 바꾸면 DB에 반영되지 않으므로 `child.setParent(this)`가 필요함

## 고아 객체: orphanRemoval

### 개념

- **관계에서 빠진 엔티티**에 remove 연산을 적용(그리고 그 엔티티로 remove를 전파)할지 여부
- `@OneToMany`, `@OneToOne`에만 있는 속성 (`@ManyToOne`에는 없음), 기본값 `false`, JPA 2.0부터
- 컬렉션이 `Map`이면 맵의 **값**에 적용

```java
@OneToMany(mappedBy = "parent", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Child> children = new ArrayList<>();
```

```java
Parent parent = em.find(Parent.class, id);
parent.getChildren().remove(0);   // 컬렉션에서 빠진 Child → 고아 → DELETE
```

### cascade REMOVE vs orphanRemoval

| | 언제 자식이 삭제되나 |
|---|---|
| `cascade = REMOVE` | **부모를 remove**할 때 그 연산이 자식에게 전파 |
| `orphanRemoval = true` | 자식이 **부모와의 관계에서 빠질 때**(컬렉션에서 제거, 1:1 참조를 다른 객체로 교체) |

- `CascadeType.ALL` + `orphanRemoval = true`를 함께 쓰면 자식의 저장·삭제가 부모 컬렉션 조작만으로 일어남 → **부모가 자식의 생명주기를 관리**하는 구조

## 면접 포인트

- **JPA 프록시란?** — `getReference()`나 지연 로딩 연관관계 자리에 들어가는, 식별자만 가진 가짜 객체. 식별자 외의 메서드를 처음 호출할 때 DB를 조회해 실제 엔티티에 위임하며, 실제 클래스와 타입이 달라 `getClass()` 비교 대신 `Hibernate.getClass()`를 써야 함.
- **왜 지연 로딩을 기본으로 쓰나?** — 즉시 로딩은 쓰지 않는 연관 엔티티까지 매번 가져오고, JPQL 조회에서는 N+1 쿼리를 만듦. `@ManyToOne`·`@OneToOne`은 기본이 EAGER라서 `fetch = LAZY`를 명시하고, 함께 필요한 경우에만 fetch join으로 가져옴.
- **LazyInitializationException은 언제, 어떻게 해결?** — 세션(영속성 컨텍스트)이 닫힌 뒤 초기화되지 않은 프록시·컬렉션에 접근할 때 발생. 트랜잭션 안에서 fetch join 등으로 필요한 데이터를 미리 가져오거나 `Hibernate.initialize()`로 초기화해 둠.
- **cascade와 orphanRemoval 차이** — cascade는 부모에 한 persist·remove 같은 연산을 자식에게 전파하는 것이고, orphanRemoval은 부모와의 관계가 끊긴 자식을 삭제하는 것.
