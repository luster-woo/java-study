## 연관관계를 나누는 기준

### 다중성

| 다중성 | 의미 (`E` → `F`) | 어노테이션 |
|---|---|---|
| 다대일 (N:1) | 여러 `E`가 하나의 `F`에 연결 | `@ManyToOne` |
| 일대다 (1:N) | 다대일의 반대 방향 (컬렉션 쪽) | `@OneToMany` |
| 일대일 (1:1) | `E` 하나와 `F` 하나 | `@OneToOne` |
| 다대다 (N:M) | 여러 `E`와 여러 `F` | `@ManyToMany` |

### 방향

- **단방향**: `E → F`로만 탐색 가능
- **양방향**: 양쪽으로 탐색 가능 — 한쪽은 **주인(owning side)**, 다른 쪽은 `mappedBy`로 주인 필드를 가리키는 **주인이 아닌 쪽(unowned / inverse side)**

### 연관관계의 주인

- DB의 FK를 실제로 관리하는 쪽 = `mappedBy`가 **없는** 쪽
- 주인이 아닌 쪽에서 바꾼 내용은 **DB에 반영되지 않음** → 연관관계를 바꾸려면 주인 쪽 필드를 바꿔야 함
- 실제로는 **양쪽을 모두** 바꿔 두는 경우가 많음 (예: 2차 캐시에 올라간 컬렉션과 DB를 맞추려면 컬렉션도 수정)

### 연관관계 어노테이션 공통 속성

| 속성 | 의미 | 기본값 |
|---|---|---|
| `cascade` | 연관 엔티티에 전파할 영속성 연산 | `{}` (전파 없음) |
| `fetch` | 즉시/지연 로딩 | `@OneToMany`·`@ManyToMany` LAZY, `@ManyToOne`·`@OneToOne` EAGER |
| `targetEntity` | 연관 엔티티 클래스 | 필드 타입(컬렉션이면 제네릭 타입)에서 추론 |
| `optional` | `~ToOne`에서 `null` 허용 여부 (`false`면 항상 연관 대상이 있어야 함) | `true` |
| `mappedBy` | 양방향에서 주인 쪽 필드 이름 | 없음 = 단방향(또는 주인) |

## 다대일 [N:1]

### 특징

- 가장 기본적인 연관관계 — DB의 **FK 하나와 그대로 대응**
- 도메인 모델의 연관관계는 대부분 이 형태
- `N` 쪽 테이블에 FK가 있고, `N` 쪽 엔티티가 주인

### 단방향

```java
import jakarta.persistence.*;

@Entity
public class Book {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)   // 기본 EAGER라서 LAZY 명시
    @JoinColumn(name = "publisher_id")   // book 테이블의 FK 컬럼
    private Publisher publisher;
}
```

### 양방향

```java
import jakarta.persistence.*;
import java.util.HashSet;
import java.util.Set;

@Entity
public class Publisher {
    @Id @GeneratedValue
    private Long id;

    @OneToMany(mappedBy = "publisher")   // Book.publisher가 주인
    private Set<Book> books = new HashSet<>();
}
```

- `Publisher.books`는 주인이 아니므로 여기에 `add`만 해서는 FK가 바뀌지 않음 → `book.setPublisher(publisher)`가 필요
- 컬렉션 필드 타입은 `Set`·`List`·`Collection` 같은 **인터페이스**로 선언 (Hibernate가 지연 컬렉션으로 바꿔 끼움)

| 컬렉션 타입 | 생각할 점 |
|---|---|
| `Set` | FK 기반 일대다는 원소가 중복될 수 없어 의미상 가장 맞음. 대신 엔티티의 `equals()`/`hashCode()`를 제대로 구현해야 함 |
| `List`, `Collection` | `equals()`/`hashCode()` 구현에 덜 민감. 순서는 따로 매핑하지 않으면 저장되지 않음 |

## 일대다 [1:N]

### 양방향 일대다 = 다대일 양방향

- `@OneToMany(mappedBy = ...)` 쪽은 사실상 다대일 양방향의 **반대편** → FK는 `N` 쪽에 있고 주인도 `N` 쪽

### 단방향 일대다

```java
@Entity
public class Customer {
    @Id @GeneratedValue
    private Long id;

    @OneToMany
    @JoinColumn(name = "customer_id")    // FK 컬럼은 Order 쪽 테이블에 있음
    private Set<Order> orders = new HashSet<>();
}
```

- `1` 쪽 엔티티가 연관관계를 관리하지만 **FK는 상대(`N` 쪽) 테이블에** 있음
- `@JoinColumn` 없이 쓰는 단방향 일대다는 조인 테이블(`@JoinTable`)을 쓰는 대표적인 경우
- Hibernate 문서: 반대편에 `@ManyToOne`이 없는 단방향 일대다는 허용은 되지만 **부자연스럽고 잘 동작하지 않으니 피하라** → 필요하면 **다대일 양방향**으로

## 일대일 [1:1]

### 방법 1 — FK + UNIQUE

- `@ManyToOne`과 거의 같고, FK 컬럼에 **UNIQUE 제약**이 붙는 형태
- FK를 가진 쪽이 주인, 반대쪽은 `mappedBy`

```java
@Entity
public class Author {
    @Id @GeneratedValue
    private Long id;

    @OneToOne(optional = false, fetch = FetchType.LAZY)
    @JoinColumn(name = "person_id", unique = true)
    private Person person;               // author 테이블에 FK
}

@Entity
public class Person {
    @Id @GeneratedValue
    private Long id;

    @OneToOne(mappedBy = "person")       // 주인이 아닌 쪽
    private Author author;
}
```

### 주인이 아닌 쪽의 지연 로딩 주의

- 위 `Person.author`는 `fetch = LAZY`를 붙이지 않았음 — 붙여도 소용이 없는 경우라서
  - 모든 `Person`에게 `Author`가 있는 것은 아니고(`optional`)
  - FK는 `author` 테이블에 있고 `person` 테이블에는 없음
  - → `Author`를 조회해 보기 전에는 참조가 `null`인지 알 수 없어 프록시를 만들 수 없음
- 모든 `Person`이 반드시 `Author`라면(`optional = false`) 지연 로딩 가능

```java
@OneToOne(optional = false, mappedBy = "person", fetch = FetchType.LAZY)
private Author author;
```

### 방법 2 — 기본 키 공유 (`@MapsId`)

```java
@Entity
public class Author {
    @Id
    private Long id;                     // @GeneratedValue 없음

    @OneToOne(optional = false, fetch = FetchType.LAZY)
    @MapsId                              // person의 PK를 Author의 PK로 사용
    private Person person;
}
```

- `author` 테이블에 별도 FK 컬럼이 없음 — **PK가 FK 역할을 겸함**
- `Person` 쪽 매핑은 그대로 (양방향이면 `@OneToOne(mappedBy = "person")`)

### 참고

- 일대일은 "~의 한 종류"(`Author`는 `Person`의 한 종류) 관계를 표현할 때가 많음 → 자바에서는 **엔티티 상속**이 더 자연스러운 대안일 수 있음

## 다대다 [N:M]

### 매핑

- 다대다는 항상 **별도의 연결 테이블(association table)**에 매핑됨
- 연결 테이블은 주인 쪽에 `@JoinTable`로 지정, 반대쪽은 `mappedBy`
- `@JoinTable` 생략 시 테이블 이름 = 두 테이블 이름을 `_`로 이은 것 (주인 쪽이 앞)

```java
@Entity
public class Customer {
    @Id @GeneratedValue
    private Long id;

    @ManyToMany
    @JoinTable(name = "customer_phone",
            joinColumns = @JoinColumn(name = "customer_id"),          // 주인(Customer)을 가리키는 FK
            inverseJoinColumns = @JoinColumn(name = "phone_id"))      // 상대(PhoneNumber)를 가리키는 FK
    private Set<PhoneNumber> phones = new HashSet<>();
}

@Entity
public class PhoneNumber {
    @Id @GeneratedValue
    private Long id;

    @ManyToMany(mappedBy = "phones")
    private Set<Customer> customers = new HashSet<>();
}
```

```
customer           customer_phone              phone_number
┌────┐            ┌─────────────┬──────────┐   ┌────┐
│ id │◄───────────│ customer_id │ phone_id │──►│ id │
└────┘            └─────────────┴──────────┘   └────┘
                  (FK 두 개뿐 — 다른 컬럼을 매핑할 곳이 없음)
```

### 다대다를 중간 엔티티로 푸는 이유

- `@JoinTable`로 정할 수 있는 것은 **테이블 이름, 양쪽 FK 컬럼, FK·UNIQUE 제약, 인덱스**뿐
  - 연결 테이블에 "주문 수량", "주문 시각" 같은 **추가 컬럼을 매핑할 자리가 없음**
- Hibernate 문서: 다대다 연관관계는 결국 **"변장한 엔티티(entity in disguise)"**로 드러나는 경우가 많음
- 그래서 연결 테이블을 **엔티티로 승격** → `@ManyToOne` 두 개(+ 필요하면 반대쪽 `@OneToMany`)로 바꿈

```
Member 1 ──── N MemberProduct N ──── 1 Product
                (count, orderedAt 같은 컬럼을 자유롭게 추가)
```

```java
import jakarta.persistence.*;
import java.time.LocalDateTime;
import java.util.ArrayList;
import java.util.List;

@Entity
public class MemberProduct {
    @Id @GeneratedValue
    private Long id;                     // 중간 엔티티 자체 식별자

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "member_id")
    private Member member;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "product_id")
    private Product product;

    private int count;                   // 연결 자체가 가진 정보
    private LocalDateTime orderedAt;
}

@Entity
public class Member {
    @Id @GeneratedValue
    private Long id;

    @OneToMany(mappedBy = "member")
    private List<MemberProduct> memberProducts = new ArrayList<>();
}
```

- 중간 엔티티도 일반 엔티티라서 조회·조건 걸기·지연 로딩 설정을 다른 다대일과 똑같이 다룰 수 있음

## 면접 포인트

- **연관관계의 주인이란?** — 양방향 연관관계에서 FK를 실제로 관리하는 쪽으로, `mappedBy`가 없는 쪽. 주인이 아닌 쪽에서 바꾼 값은 DB에 반영되지 않으므로 주인 쪽을 반드시 설정하고, 보통 편의 메서드로 양쪽을 함께 맞춤.
- **단방향 일대다를 피하는 이유** — 연관관계는 `1` 쪽 엔티티가 관리하는데 FK는 `N` 쪽 테이블에 있어 매핑이 부자연스러움. Hibernate 문서도 피하라고 하며, 다대일 양방향으로 바꾸는 것이 일반적.
- **`@ManyToMany`를 실무에서 잘 안 쓰는 이유** — 연결 테이블에 FK 두 개만 매핑할 수 있어 수량·시각 같은 추가 정보를 둘 수 없음. 연결 테이블을 중간 엔티티로 만들어 다대일 두 개로 풂.
- **일대일 매핑 방법 두 가지** — FK에 UNIQUE를 건 방식(다대일과 거의 같음)과 `@MapsId`로 PK를 공유하는 방식. FK가 없는 쪽(`mappedBy` 쪽)은 연관 대상이 없을 수 있으면 지연 로딩이 되지 않음.

## 참고

- Hibernate Introduction 문서의 다대다 절(3.19)은 연결 테이블과 "변장한 엔티티" 설명까지만 참고함 — 그 뒤의 예시는 읽지 못해 노트에 넣지 않음. 연결 테이블의 컬럼 구성은 `@JoinTable` API 문서(속성 목록) 기준.
- 원문 예제의 `mappedBy = Book_.PUBLISHER`(메타모델 생성기 상수)는 노트에서 문자열 `"publisher"`로 바꿈.
- 중간 엔티티의 PK를 복합 키(`@IdClass`, `@EmbeddedId`)로 두는 방법도 있지만 이 노트에서는 다루지 않음.
